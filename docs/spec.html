vfio_nvme 仕様書

このリポジトリは、PC に挿さっているネットワークカードを OS に任せず自分の プログラムから直接動かし、その上に通信の仕組みとストレージの仕組みを全部 自前で実装して、Linux 標準の実装とどちらが速いかを測る実験装置です。

この文書について

誰のための文書か

C 言語は読み書きできるが、ネットワークとデバイスドライバの知識は無い人を 想定しています。具体的には、

  • ポインタ・構造体・ビット演算は分かる
  • malloc() は知っているが、ハードウェアがメモリを直接読み書きする話は知らない
  • ソケット通信は書いたことがあるかもしれないが、通信路の上を実際にどんな バイト列が流れているかは知らない
  • SSD やネットワークカードの「中の人」が何をしているかは知らない

という人が、最初から順番に読んで、途中で知らない言葉に出会わずに 最後まで到達できることを目標にしています。

読み方

  • 最初から順に読むことを前提に書いています。専門用語は必ず「初めて出て くる場所」で説明し、それ以降は説明済みのものとして使います。
  • 略語や専門用語には、各章の最初の 1 回だけ 用語集 への リンクを張ってあります。忘れたら飛んでください。
  • 各章の終わりに 「ソースのどこを読むか」 という節があります。文書と 実際のコードを行き来するための道しるべです。
  • 左に章の一覧を出したいときは docs/spec.html(この文書から生成した HTML 版)。 章の絞り込みと、いま読んでいる章のハイライトが付きます。
  • 急いでいる人は、第 1 章(何をするソフトか)と 第 17 章(全体アーキテクチャ)と 第 20 章(1 つの I/O を 最後まで追う)だけでも全体像がつかめます。

第 I 部 はじめに

第 1 章 このソフトは何か

1.1 まず 10 個だけ

この文書を読むのに最低限必要な言葉を、先に 10 個だけ説明します。 ここから先は、この 10 個を知っているものとして話を進めます。

(1) カーネルとユーザ空間

カーネルとは OS の中核部分のことです。メモリの管理、 プロセスの切り替え、ハードウェアの操作といった「特権が要る仕事」を担当し、 CPU の特権モードで動きます。

一方、私たちが普段書くプログラム(main() があるあれ)は ユーザ空間で動きます。ユーザ空間のプログラムは ハードウェアを直接触れません。触りたければカーネルにお願いします。 このお願いがシステムコールです(read()、write()、 send() など)。

(2) デバイスドライバ

デバイスドライバは、特定のハードウェアの操作方法を知って いるプログラムです。普通はカーネルの一部として動きます。「このカードに データを送らせるには、この番地にこの値を書いて…」という手順を全部知って いるのがドライバです。

(3) NIC(ネットワークカード)

NIC(Network Interface Card)は、LAN ケーブルや光ファイバに 繋がる部品です。PC の中では PCI Express というスロットに挿さっています。 このリポジトリが相手にするのは Mellanox(現 NVIDIA)の ConnectX-4 と いう製品で、25 ギガビット/秒の速度が出ます。

(4) SSD

SSDはフラッシュメモリを使った記憶装置です。この文書で重要な のは中身の物理ではなく、SSD と会話する手順のほうです。

(5) NVMe

NVMe(Non-Volatile Memory Express)は、SSD と会話するための 決まりごとです。「読め」「書け」といった命令をどんなバイト列で表すか、 それをどうやって SSD に渡すかが決められています。

(6) NVMe-oF(ネットワーク越しのストレージ)

普通、SSD は自分の PC の中に挿さっています。これをネットワークの向こう側に 置いて、あたかも手元にあるかのように使うのが NVMe-oF(NVMe over Fabrics)です。「読め」という命令を ネットワークに乗せて送り、データを送り返してもらいます。

(7) TCP

TCPは、ネットワーク越しにバイトの列を、順番どおりに、 欠けずに届けるための決まりごとです。インターネットのほとんどの通信が これを使っています。

(8) RDMA

RDMA(Remote Direct Memory Access)は、相手のコンピュータの CPU を働かせずに、相手のメモリを直接読み書きする技術です。TCP より速い 代わりに、専用のネットワークカードが要ります。この文書では RoCEv2 という方式を扱います。

(9) スループットとレイテンシ

スループットは「1 秒間に何バイト運べるか」、 レイテンシは「1 回の要求に何秒かかるか」です。 この 2 つは別物で、片方が良くても片方が悪いことがあります。

(10) ターゲットとイニシエータ

ストレージの世界では、命令を出す側をイニシエータ、 命令を受けて実行する側をターゲットと呼びます。 普通のクライアント/サーバと同じ関係です。SSD を貸す側がターゲット、 借りる側がイニシエータです。

1.2 このソフトがやること

一言でいうと、

NIC を OS に任せず自分のプログラムから直接動かし、その上に通信の仕組み (Ethernet / IP / TCP)とストレージの仕組み(NVMe-oF)を全部自前で実装 して、Linux 標準の実装とどちらが速いかを測る。

です。特徴的なのは、イニシエータとターゲットの両方が同じプログラムの中に いることです。1 つのプロセスの中に「SSD を貸す側」と「借りる側」が同居して いて、実際のネットワークケーブルを通してお互いに通信します。

   ┌──────────────────────────────────────────────┐
   │      1 個のプロセス(vfio_nvme)              │
   │                                              │
   │   イニシエータ            ターゲット         │
   │   (借りる側)            (貸す側)         │
   │       │                      ↑              │
   │       │  NVMe-oF のコマンド  │              │
   │       ↓                      │              │
   │   自作 TCP/IP            自作 TCP/IP         │
   │       │                      ↑              │
   │   自作 NIC ドライバ      自作 NIC ドライバ   │
   └───────┼──────────────────────┼───────────────┘
           │                      │
       ┌───┴───┐              ┌───┴───┐
       │ PF0   │              │ PF1   │   ← 1 枚の NIC の 2 つのポート
       └───┬───┘              └───┬───┘
           │                      │
           └──── ネットワーク ────┘

「同じプロセスの中で通信して意味があるのか」と思うかもしれませんが、 フレームは本当に物理的にケーブルを通って往復します。ソフトウェア的な 近道はしていません。

このプログラムを起動すると、対話シェルが立ち上がります。

1.4 何をしないか(目的外のこと)

これは実験装置であって、製品ではありません。次のことは目的にしていません。

  • 汎用性: ConnectX-4 系の NIC でしか動きません。他社製カードは対象外です。
  • 堅牢性: 想定外の入力に対して落ちないことは保証していません。
  • セキュリティ: 認証も暗号化もありません(誰でも接続できます)。 ネットワークから隔離された実験用の配線でのみ使います。
  • 永続性: 「SSD」の中身はメモリ上の配列です。プロセスを終了すると 消えます。本物のフラッシュメモリは繋がっていません。
  • 複数プロセスからの共有: NIC を 1 プロセスが占有します。

「SSD の中身がメモリ」というのは重要な点です。このプロジェクトが測って いるのは通信の速さであって、記憶装置の速さではありません。 記憶装置を 本物にすると、そちらが遅くて通信の性能差が見えなくなるからです。

第 2 章 なぜカーネルを通さないのか

2.1 普通のプログラムがデータを送るとき

C でネットワークプログラムを書くと、こうなります。

send(sock, buf, len, 0);

この 1 行の裏側で何が起きているかを追うと、こうです。

  あなたのプログラム(ユーザ空間)
        │  buf にデータがある
        │
        │ ① send() を呼ぶ = システムコール
        ▼
  ┌─────────────────────────────────────┐
  │ カーネル                            │
  │                                     │
  │ ② buf の中身をカーネルのメモリへ    │  ← メモリコピー 1 回目
  │    コピーする                       │
  │                                     │
  │ ③ TCP の処理(順番の管理、再送の    │
  │    ための保存、確認応答の待ち…)   │
  │                                     │
  │ ④ IP のヘッダを付ける               │
  │ ⑤ Ethernet のヘッダを付ける         │
  │                                     │
  │ ⑥ ドライバに渡す                    │
  └──────────────┬──────────────────────┘
                 │ ⑦ NIC に「送れ」と伝える
                 ▼
              NIC がケーブルへ送出

ここで 2 種類のコストが発生します。

(a) メモリコピー

②で、あなたのバッファからカーネルのバッファへデータを丸ごと写します。 1 バイトも減っていないのに、CPU がわざわざ全部読んで全部書きます。 64 キロバイトのデータなら 64 キロバイト読んで 64 キロバイト書きます。

なぜコピーが要るかというと、カーネルはユーザ空間のメモリを信用できない からです。send() を呼んだ直後にあなたのプログラムが buf を書き換えたら、 送信中のデータが化けてしまいます。だから安全な場所に写します。

(b) コンテキストスイッチ

①でユーザ空間からカーネルへ、処理が終わったらカーネルからユーザ空間へ、 CPU の動作モードが切り替わります。この切り替えにはレジスタの退避・復帰、 場合によってはキャッシュの入れ替えが伴います。1 回あたりのコストは小さい (数百ナノ秒程度)のですが、1 秒間に何万回も起きると効いてきます。

前章のベンチマークで IOPS 53617 という数字がありました。1 秒に 5 万回の 命令です。1 命令が 2 回の切り替えを伴うと 10 万回。仮に 1 回 500 ナノ秒なら 合計 50 ミリ秒 — 1 秒のうち 5% をモード切り替えだけで使う計算になります。

2.2 このプロジェクトのやり方

このプロジェクトは、上の図のカーネルの部分を全部ユーザ空間に持ってきます。

  vfio_nvme(ユーザ空間の 1 プロセス)
        │
        │ 自前の TCP 処理
        │ 自前の IP ヘッダ付け
        │ 自前の Ethernet ヘッダ付け
        │ 自前の NIC ドライバ
        │
        │ NIC のレジスタに直接書く
        ▼
     NIC がケーブルへ送出
  • システムコールが無いので、モードの切り替えが起きません。
  • コピーが減らせます。 データの置き場所を自分で決められるので、 「最初から NIC が読める場所に置いておく」ことができます (これをゼロコピーと呼びます)。

この考え方自体は珍しいものではなく、DPDK(ネットワーク用)や SPDK(ストレージ用)という有名なフレームワークが同じことをしています。 このプロジェクトはそれらを使わず、同じことを一から書いているわけです。

2.3 代償

いいことばかりではありません。

(a) OS の保護が効かない

カーネルは「不正なアドレスを NIC に教えてしまう」ようなミスから守って くれていました。それが無くなります。間違ったアドレスを NIC に渡すと、 NIC が無関係なメモリを書き換えます。 これを防ぐ仕組みが IOMMU で、第 3 章で説明します。

(b) NIC を独占する

カーネルのドライバは 1 枚の NIC を全プロセスで共有させてくれますが、 この方式では 1 プロセスが丸ごと占有します。同じマシンの他のプログラムは、 その NIC を使えません。

(c) 全部自分で書く必要がある

ARP も、IP も、TCP の再送も、輻輳制御も、全部自分で書きます。 このリポジトリが約 33,000 行あるのはそのためです。しかも 「普通に通信できる」だけでは足りません。ケーブルが抜けた、相手が 落ちた、パケットが失われた、といった異常系も全部自分で面倒を見ます。

(d) デバッグが難しい

tcpdump も netstat も使えません。カーネルが知らないところで通信して いるからです。だからこのプロジェクトには、自分で自分を観測するための 仕組み(ts_log というリングバッファや、たくさんの検査コマンド)が 組み込まれています(第 27 章)。

2.4 どのくらい速いのか

README.md に Linux 標準実装との比較表があります。ここでは傾向だけ 述べると、NVMe/TCP では Linux カーネル実装の 3〜8 倍の速度が出ています。

ただしこの比較は対等ではありません。Linux 側はネットワーク名前空間を 経由した本物の TCP スタックを通っているのに対し、こちらは同一プロセス内で 折り返しています。順位そのものより「変更の前後で同じ列を比べる」ことに 意味がある、という位置づけです。詳しくは 第 22 章 で説明します。

第 3 章 PC とデバイスはどう繋がっているか

3.1 PCI Express — 部品を挿す口

PC のマザーボードには、部品を挿すための細長いスロットがあります。 グラフィックスカードや NIC を挿すあれです。この規格が PCI Express(略して PCIe)です。

PCIe に挿さった部品(デバイスと呼びます)は、01:00.0 のような アドレスを持ちます。これは「バス番号 01、デバイス番号 00、機能番号 0」の 意味です。Linux では次のように一覧できます。

$ lspci
01:00.0 Ethernet controller: Mellanox Technologies MT27710 Family [ConnectX-4 Lx]
01:00.1 Ethernet controller: Mellanox Technologies MT27710 Family [ConnectX-4 Lx]

このプロジェクトが使う NIC は、1 枚のカードで 2 つのポートを持っています。 だから 01:00.0 と 01:00.1 の 2 つに見えます。この 1 つ 1 つを PF(Physical Function、物理機能)と呼び、この文書では PF0、PF1 と書きます。

3.2 レジスタと MMIO — 番地に代入するとハードが動く

デバイスを操作するとは、具体的には何をすることでしょうか。

答えは、デバイスが持っている「レジスタ」に値を書いたり読んだりすること です。レジスタとは、デバイスの中にある小さな記憶場所で、 「ここに 1 を書いたら送信開始」「ここを読むと今の状態が分かる」といった 役割が製品ごとに決められています。

問題は「どうやってそのレジスタに書くのか」です。仕組みはこうです。

デバイスのレジスタを、CPU から見たメモリの番地に割り当ててしまう。

これを MMIO(Memory-Mapped I/O、メモリマップド I/O)と 言います。C で書くとこうなります。

volatile uint32_t *reg = (volatile uint32_t *)0xf7200000;  /* デバイスの番地 */
*reg = 1;                     /* ← この代入がデバイスへの命令になる */
uint32_t status = *reg;       /* ← この読み出しがデバイスへの問い合わせになる */

代入文がハードウェアへの命令になります。 ここが、普通のプログラミングと デバイス操作の一番の違いです。

volatile が付いているのが重要です。コンパイラは「同じ番地に 2 回書いたら 1 回にまとめよう」「さっき読んだ値を使い回そう」といった最適化をしますが、 MMIO ではその最適化が命取りになります。volatile はそれを禁じます。

この「デバイスのレジスタが割り当てられたアドレスの範囲」を BAR(Base Address Register)と呼びます。1 つのデバイスが 複数の BAR を持つこともあります。

3.3 3 種類のアドレス

ここからが混乱しやすいところです。同じ 1 バイトのメモリを指すのに、 見る立場によって 3 つの違う番号が使われます。

   あなたのプログラムから見た番地       [仮想アドレス]
              |
              |  CPU の MMU(メモリ管理ユニット)が変換
              v
   メモリチップ上の実際の位置           [物理アドレス]
              ^
              |  IOMMU が変換
              |
   デバイスから見た番地                 [IOVA]

(1) 仮想アドレス

malloc() が返すポインタの値です。プロセスごとに独立していて、別のプロセス の同じ番地は別の場所を指します。CPU の中の MMU(Memory Management Unit) という回路が、これを物理アドレスに変換しています。普段プログラムを書くとき、 私たちはこれしか見ていません。

(2) 物理アドレス

メモリチップ上の本当の位置です。OS だけが知っています。

(3) IOVA

デバイスから見た番地です。「IO Virtual Address」の略です。 なぜ 3 つ目が要るのかは、次の節で説明します。

3.4 DMA — デバイスがメモリを直接読み書きする

NIC が 1 ギガバイトのデータを送るとき、CPU がそのデータを 1 バイトずつ レジスタに書いていたら、CPU の時間が全部それに消えてしまいます。

そこで実際には逆のことをします。

CPU は「このアドレスから 1500 バイト送れ」とだけ NIC に教える。 NIC が自分でメモリを読みに行く。

これが DMA(Direct Memory Access)です。デバイスがメモリバスに 直接アクセスして、CPU を介さずにデータを読み書きします。受信のときは逆に、 NIC が受け取ったデータを勝手にメモリへ書き込みます。

ここで問題が起きます。 CPU に教えるアドレスは仮想アドレスですが、 NIC は MMU の外側にいるので仮想アドレスを理解できません。かといって 物理アドレスを直接教えると、危険なことになります。

ユーザ空間のプログラムが「物理アドレス 0 番地に受信データを書け」と NIC に命じたら、OS のカーネルが上書きされて PC が壊れます。

3.5 IOMMU — デバイス用の MMU

この危険を防ぐのが IOMMU(Input/Output MMU)です。 名前のとおり、デバイス専用の MMU です。

  デバイスが「IOVA = 0x1000 を読め」と言う
              |
              v
      +---------------+
      |    IOMMU      |  <- 「このデバイスは IOVA 0x1000 を
      |  (変換表)   |      物理 0x8a3f2000 として使ってよい」
      +-------+-------+      という表を OS が事前に作っておく
              v
      物理アドレス 0x8a3f2000 を読む

IOMMU があると、

  • 表に載っていない番地にはアクセスできません。 間違ったアドレスを渡して も、他人のメモリは壊せません(アクセスが失敗するだけです)。
  • デバイスごとに別の表を持てるので、デバイスを 1 つのプロセスに安全に 貸し出せます。

この「安全に貸し出せる」という性質が、ユーザ空間からデバイスを操作できる 根拠になっています。次章の VFIO はこの仕組みの上に乗っています。

3.6 hugepage — なぜ普通のメモリでは困るのか

CPU のメモリ管理は 4 キロバイトを 1 単位(ページ)として行います。 malloc() で 1 メガバイト取ると、それは物理的には 4KB の断片 256 個に 散らばっているかもしれません。仮想アドレス上は連続に見えても、です。

DMA でこれを使おうとすると、256 個の断片それぞれについて IOMMU の表に 登録する必要が出てきます。しかも断片の物理アドレスは連続していないので、 「ここから 1 メガバイト読め」と一言で NIC に伝えられません。

そこで hugepage を使います。これは 2 メガバイト(または 1 ギガバイト)を 1 ページとする仕組みで、Linux では事前に確保しておきます。

$ echo 1024 | sudo tee /proc/sys/vm/nr_hugepages    # 2MB × 1024 = 2GB を予約

2MB が物理的に連続していることが保証されるので、大きな DMA 用バッファを 少ない登録回数で作れます。

このプロジェクトは「SSD の中身」をメモリ上に持つので、それだけで 268 メガバイト使います。加えて各種のバッファがあるため、hugepage を 1024 ページ(2 ギガバイト)確保して動かしています。

3.7 割り込みとポーリング

デバイスが「仕事が終わりました」と知らせる方法は 2 つあります。

割り込み: デバイスが CPU に信号を送り、CPU が今の 仕事を中断して対応する。暇なときに CPU を消費しない代わりに、 1 回あたりの反応が遅い(数マイクロ秒)。

ポーリング: CPU が「終わった?」と繰り返し見に行く。 CPU を食い続ける代わりに、反応が速い。

このプロジェクトは全面的にポーリングを使っています。 理由は速度です。 1 秒に 5 万回の I/O を処理する場面では、割り込みの遅延と処理コストが 無視できません。CPU を 1 コア丸ごと「見張り」に使うほうが速いのです。

DPDK や SPDK も同じ選択をしています。「CPU がもったいない」のではなく、 「速度のために CPU を投資している」と考えてください。

補足: mmio_write64() が独立して存在するのには理由があります。 64 ビットの値は 1 回の命令で書かなければならない場面があり、 32 ビット × 2 回に分けると壊れます。実際にこのプロジェクトでは、 32 ビット 2 回に分けていたせいで数十万コマンドに 1 回エラーが出る という不具合を踏んでいます(CLAUDE.md に記録があります)。

第 4 章 VFIO — ユーザ空間からデバイスを掴む

4.1 VFIO とは

VFIO(Virtual Function I/O)は、Linux が用意している 「デバイスをユーザ空間のプログラムに貸し出す」仕組みです。もともとは 仮想マシンにデバイスをそのまま見せる用途(PCI パススルー)のために 作られましたが、DPDK や SPDK のようなユーザ空間ドライバもこれを使います。

VFIO が提供するのは次の 4 つです。

  1. デバイスのレジスタ領域(BAR)を mmap() でプロセスのメモリ空間に貼る
  2. 設定情報(コンフィグ空間)の読み書き
  3. IOMMU の表への登録(このメモリをこのデバイスに見せてよい、の宣言)
  4. 割り込みの受け取り(このプロジェクトはポーリングなので使いません)

4.2 デバイスをカーネルから取り上げる

普通、NIC はカーネルのドライバ(mlx5_core)が握っています。 これを VFIO に渡すには、バインドを付け替えます。

# 今どのドライバが握っているか
$ lspci -nnks 01:00.0
    Kernel driver in use: mlx5_core

# vfio-pci に付け替える
$ echo vfio-pci | sudo tee /sys/bus/pci/devices/0000:01:00.0/driver_override
$ echo 0000:01:00.0 | sudo tee /sys/bus/pci/devices/0000:01:00.0/driver/unbind
$ echo 0000:01:00.0 | sudo tee /sys/bus/pci/drivers_probe

このカードは mlx5_core か vfio-pci のどちらか一方にしかバインドでき ません。 VFIO に渡している間は、Linux から見て NIC が消えます (ip link に出てきません)。実験が終わったら戻す必要があります。

4.3 IOMMU グループ — まとめてしか貸せない

VFIO はデバイス単位ではなくグループ単位で貸し出します。 IOMMU グループとは、「IOMMU が互いを区別できない デバイスの集まり」です。

区別できないものを別々のプロセスに貸すと、片方がもう片方のメモリを 覗けてしまいます。だからグループ全体を 1 つの借り手に貸すという 規則になっています。

このプロジェクトの NIC は、2 つの PF が同じグループに入っています。

$ ls /sys/kernel/iommu_groups/2/devices/
0000:00:01.0  0000:01:00.0  0000:01:00.1

このため、PF0 だけを VFIO に、PF1 をカーネルに、という分け方ができません。 「2 ポートとも自作ドライバが握る」か「2 ポートともカーネルが握る」かの 2 択です。この制約が、後の章で出てくる検証方法の選択に影響します。

4.4 使う手順

C のコードから見ると、おおよそ次の順序です。

(1) /dev/vfio/vfio を開く                      -> コンテナができる
(2) /dev/vfio/<グループ番号> を開く            -> グループの取っ手
(3) グループをコンテナに入れる
(4) コンテナに IOMMU の種類を設定する
(5) グループからデバイスの取っ手をもらう
(6) デバイスの BAR の情報を問い合わせる
(7) BAR を mmap() する                         -> レジスタが触れるようになる
(8) DMA 用のメモリを確保して IOMMU に登録する  -> デバイスが読み書きできる

(8) が 第 3 章 で説明した IOMMU への登録です。「この仮想アドレスの 領域を、この IOVA としてデバイスに見せてよい」という宣言をします。

このプロジェクトでは、IOVA の値を物理アドレスと同じにするという単純な 方針を採っています(アイデンティティマッピングと呼びます)。変換表が 単純になり、デバッグしやすくなります。

4.5 このプロジェクトでの実装

VFIO を触る部分はプラットフォーム依存なので、src/platform/x86-linux/ に隔離されています。上位のコード(mlx5.c など)は、 include/platform.h で決められた少数の関数だけを使います。

上位のコード(アーキテクチャ非依存)
   |   dma_alloc()      … DMA できるメモリをください
   |   dma_cpu_to_dev() … このポインタをデバイス用の番地に直して
   v
include/platform.h(契約)
   ^
   |  実装
src/platform/x86-linux/hal_dma.c  … VFIO / hugepage を使った実装
src/platform/x86-linux/vfio.c     … VFIO そのものの操作

この分離のおかげで、元は Raspberry Pi 5 のベアメタル環境(OS 無し)で 動いていたコードを、x86 の Linux ユーザ空間に移植できています。

4.6 実際に起きた問題

プロセスが残っているとデバイスを返せません。 VFIO はプロセスが デバイスを掴んでいる間、unbind を待たせます。プログラムが異常終了して 残っていると、unbind が無期限にブロックします。実際に 15 分以上 止まった記録があります。

$ dmesg
vfio-pci 0000:01:00.0: No device request channel registered,
                       blocked until released by user

対処は、残っているプロセスを探して落とすことです。詳しい手順は CLAUDE.md にあります。

第 5 章 ネットワークカードの動かし方

前章までで「デバイスのレジスタを触れる」「デバイスにメモリを見せられる」 状態になりました。この章では、実際に NIC を目覚めさせてフレームを やりとりできるようにするまでを説明します。

対象は Mellanox ConnectX-4 です。この系統のカードは HCA(Host Channel Adapter)と呼ばれます。

5.1 レジスタを直接叩くだけでは動かない

第 3 章 で「レジスタに書けばデバイスが動く」と説明しましたが、 現代の高機能な NIC はそこまで単純ではありません。

このカードの中にはファームウェア(FW)という 小さなプログラムが動いています。カードを設定するには、レジスタを直接 叩くのではなく、FW にコマンドを送って依頼します。

   あなたのプログラム
        |
        |  ① コマンドをメモリ上に書く(例: 「送信キューを作れ」)
        |  ② レジスタを叩いて「置いたよ」と知らせる
        v
   +--------------------------+
   |  NIC の中のファームウェア |  ③ DMA でコマンドを読む
   |                          |  ④ 実行する
   +--------------------------+  ⑤ 結果をメモリに書き戻す
        |
        |  ⑥ 完了したかどうかをポーリングで確認する
        v
   あなたのプログラム

この①〜⑥のやりとりの場を コマンドキュー(cmdq)と 呼びます。NIC の設定はすべてこのコマンドキュー経由で行います。

コマンドには番号(オペコード)が振られています。たとえば、

オペコード名前意味
0x100ENABLE_HCAカードを目覚めさせる
0x800ALLOC_UARdoorbell 用の領域をください
0x400CREATE_CQ完了通知キューを作って
0x500CREATE_QP通信の口を作って

このプロジェクトは、これらのコマンドの中身(何バイト目に何を書くか)を Linux カーネルのヘッダファイル mlx5_ifc.h を実際に読んで確認しながら 実装しています。推測で書くと、数バイトずれただけで動かなくなります。

5.2 キューとリングバッファ

NIC とのデータのやりとりは、キューを通して行います。キューの実体は リングバッファです。C プログラマにはおなじみの、 配列と 2 つの添字でできた構造です。

     配列(実体はメモリ上の連続領域)
   +----+----+----+----+----+----+----+----+
   | 0  | 1  | 2  | 3  | 4  | 5  | 6  | 7  |
   +----+----+----+----+----+----+----+----+
          ^              ^
          |              |
      consumer       producer
      (読む側)       (書く側)

書く側が producer を進め、読む側が consumer を進めます。末尾まで 行ったら先頭に戻る(だから「リング」)。片方が CPU、もう片方が NIC に なります。

このカードには 4 種類のキューがあります。

略語正式名向き何を入れるか
SQSend QueueCPU → NIC「これを送れ」という指示
RQReceive QueueCPU → NIC「受信したらここに入れて」という空きバッファ
CQCompletion QueueNIC → CPU「終わったよ」という通知
EQEvent QueueNIC → CPU「異常が起きたよ」という通知

RQ の向きに注意してください。 受信キューに入れるのは「受信データ」では なく、「受信データを入れるための空のバッファの場所」です。NIC はフレームを 受け取ると、RQ から空きバッファを 1 つ取り出して、そこに DMA で書き込みます。

5.3 WQE と CQE

キューに入れる 1 個 1 個の要素にも名前があります。

  • WQE(Work Queue Element、「ウィッキー」と読む人が多い): SQ や RQ に入れる作業指示書。「このアドレスから 1500 バイトを送れ」 といった内容が、決められたバイト配置で書かれています。
  • CQE(Completion Queue Entry): CQ に入る完了報告。 「さっきの作業は成功した」「エラーコード 0x12 で失敗した」といった情報が 入っています。

送信の流れを具体的に書くと、こうなります。

① 送りたいデータを DMA できるメモリに用意する
② SQ の空きスロットに WQE を書く
     - 「送信」という種別
     - データのアドレス(IOVA)と長さ
     - Ethernet ヘッダ(短いものは WQE に直接埋め込める)
③ doorbell を鳴らす(次節)
④ 別のタイミングで CQ をポーリングして、完了を確認する

5.4 doorbell — 「置いたよ」の伝え方

WQE をメモリに書いただけでは NIC は気付きません。「新しい指示を置いた」 と教える必要があります。これが doorbell(呼び鈴)です。

doorbell の正体は MMIO への書き込みです。専用に割り当てられたレジスタ領域 (UAR、User Access Region と言います)の特定の番地に、 「今 SQ のどこまで書いたか」を示す番号を書きます。

/* イメージ(実際のコードとは異なります) */
sq->wqe[index] = ...;          /* ① WQE を書く */
__asm__ volatile("" ::: "memory");  /* ② 順序を守らせる */
mmio_write64(uar + DOORBELL_OFFSET, packed_value);  /* ③ 鳴らす */

②のメモリバリアが重要です。CPU は性能のために書き込みの順序を入れ替える ことがありますが、doorbell が WQE より先に届くと、NIC は書きかけの WQE を 読んでしまいます。バリアはそれを禁じます。

このカードには BlueFlame という高速化の仕組みもあり、小さなデータなら doorbell と一緒に WQE そのものを MMIO で書き込めます。DMA の往復が減るぶん 速くなります。

実際に踏んだ不具合: この doorbell を「32 ビット × 2 回」で書いていた ために、数十万コマンドに 1 回だけエラーが出るという問題がありました。 8 バイトはアトミックに(1 回の 64 ビット書き込みで)書かなければ なりません。第 3 章 の補足で触れたのがこれです。

5.5 bring-up の順序

カードを使える状態にすることを bring-up と呼びます。順序には 依存関係があり、飛ばすと失敗します。このプロジェクトの順序は次のとおりです。

 1. コマンドキューの初期化          … これが無いと何も依頼できない
 2. ENABLE_HCA                      … カードを目覚めさせる
 3. 能力の問い合わせ(QUERY_HCA_CAP)… 何ができるカードかを聞く
 4. 初期化ページの供給              … FW が使う作業用メモリを渡す
 5. INIT_HCA                        … 初期化
 6. UAR の確保                      … doorbell を書く場所
 7. EQ の作成                       … 異常通知の受け皿
 8. PD の確保                       … 「保護ドメイン」(次節)
 9. MKey の作成                     … メモリの使用許可証(次節)
10. CQ の作成                       … 完了通知の受け皿
11. TIS / TIR の作成                … 送受信の「型」を決めるオブジェクト
12. SQ / RQ の作成                  … 実際の送受信キュー
13. フローステアリングの設定        … 届いたフレームをどこへ送るか(5.7)
14. ポートを up にする

なぜこの順序かは、後のものが前のものを参照するからです。たとえば CQ を作るコマンドには「どの UAR を使うか」を書く欄があるので、UAR が先です。

5.6 PD と MKey — メモリの使用許可証

PD(Protection Domain、保護ドメイン)と MKey(Memory Key)は、NIC にメモリを使わせるための許可証です。

第 3 章 で IOMMU の話をしました。IOMMU は「OS がデバイスに許した 範囲」を決めますが、MKey はその内側で、さらにカードの中で使う許可証です。

  MKey = 「このアドレスから この長さ の範囲を、読み書きしてよい」
         という登録。番号(キー)が発行される。

  WQE には「このデータは MKey 番号 X の中の、オフセット Y にある」と書く。

なぜ二重になっているかというと、RDMA では相手にこの番号を 教えるからです(第 15 章)。「私のメモリのここを読んでいいですよ、 鍵はこれです」と渡す仕組みなので、鍵という概念が要ります。

PD はその MKey たちをまとめるグループです。異なる PD の資源は互いに アクセスできません。

5.7 フローステアリング — 届いたフレームをどこへ入れるか

NIC に 1 本のケーブルから色々なフレームが届きます。それを 「どの受信キューに入れるか」を決める仕組みが フローステアリングです。

高性能な NIC は受信キューを何本も持てるので、たとえば 「宛先ポート 80 番のパケットはキュー 0 へ、それ以外はキュー 1 へ」 といった振り分けができます。CPU コアごとにキューを分ければ、 複数コアで並列に処理できます。

このプロジェクトは単純で、全部を 1 本のキューに入れる規則 (catch-all、キャッチオール)を 1 つ登録しているだけです。振り分けは ソフトウェア側(第 6 章 以降)で行います。

副作用: この catch-all のせいで、RDMA 用のフレームまで 通常の受信キューに複製されて届きます。 これは長らく 「未対応プロトコル、無視」というログとして無害に流れていたのですが、 あとで UDP を実装したときに「待ち受けていないポート宛」と判定され、 エラー応答を大量に送り返すという問題を引き起こしました (第 9 章 で詳述)。

5.8 QP — RDMA 用の「通信の口」

ここまでの SQ / RQ / CQ は Ethernet フレームをやりとりするための仕組み でした。RDMA を使うときは、別の道具立てになります。

QP(Queue Pair、キューペア)は、その名のとおり 送信キューと受信キューを 1 組にしたもので、RDMA の通信単位です。 TCP のソケットに相当すると考えると分かりやすいでしょう。

QP には状態があり、決められた順に遷移させます。

  RESET  →  INIT  →  RTR  →  RTS
  (初期)  (初期化) (受信可) (送受信可)
                    Ready     Ready
                    To Receive To Send

どのパラメータをどの遷移で設定するかが決まっています。 たとえば 「相手から同時に何個の RDMA 読み出しを受け付けるか」という設定は INIT→RTR でしか反映されません。RTR→RTS で書いても FW は保持しません。

実際に踏んだ不具合: この設定を間違った遷移で書いていたため、 相手が 2 個目の読み出しを投げた瞬間にエラーになる、という問題が ありました。これを直したことで書き込み性能が 2.3 倍になっています (第 15 章 で詳述)。

第 III 部 ネットワークの基礎と、この実装

ここからはソフトウェアの話です。ケーブルの上を流れるバイト列がどんな形を していて、それをこのプログラムがどう組み立て、どう解釈するかを説明します。

第 6 章 パケットは入れ子の箱

6.1 一番大事な図

ネットワークの話で最初に理解すべきなのは、データが入れ子の箱に入って 運ばれるということです。この 1 枚の図が第 III 部と第 IV 部の土台になります。

 ケーブルの上を流れる 1 個のかたまり([フレーム] と呼ぶ)

 +----------------+------------+-------------+---------------------------+
 | Ethernet ヘッダ | IP ヘッダ  | TCP ヘッダ  |  中身(アプリのデータ)   |
 |    14 バイト    | 20 バイト  |  20 バイト  |                           |
 +----------------+------------+-------------+---------------------------+
 |<-- どの機械へ ->|<-- どの  ->|<-- どのプロ->|                          |
 |    (MAC)      |   IP へ    |  グラムへ    |                          |
 +----------------+------------+-------------+---------------------------+
                  |<--------------- IP から見た「中身」  --------------->|
                               |<------ TCP から見た「中身」  ---------->|
  • 一番外側の Ethernet ヘッダは「同じケーブルに繋がって いる機械のうち、どれ宛か」を書きます。宛先は MAC アドレス(48 ビットの機器固有番号)です。
  • 次の IP ヘッダは「世界中のどのコンピュータ宛か」を書きます。 宛先は IP アドレスです。
  • 次の TCP ヘッダは「そのコンピュータの中のどのプログラム 宛か」を書きます。宛先はポート番号です。
  • その中身が、実際に運びたいデータです。

各層は「自分のヘッダ」だけを見て、その内側はただのバイト列として扱います。 だから層を積み替えられます(IP の上に TCP でも UDP でも載せられる)。

このプロジェクトでは、さらに内側に NVMe のコマンドが入ります。

 +----------+---------+----------+---------------------------------+
 | Ethernet |   IP    |   TCP    |   NVMe/TCP の PDU               |
 +----------+---------+----------+---------------------------------+
                                 | +---------+-------------------+ |
                                 | | PDU ヘッダ |  NVMe コマンド  | |
                                 | +---------+-------------------+ |
                                 +---------------------------------+

PDU が何かは 第 14 章 で説明します。今は 「TCP の中にさらに箱がある」とだけ分かれば十分です。

6.2 バイトオーダー — 数値の並べ方

uint32_t x = 0x12345678; をメモリに置いたとき、バイトの並びは CPU に よって違います。

  リトルエンディアン(x86、ARM の通常設定): 78 56 34 12
  ビッグエンディアン                      : 12 34 56 78

ネットワークのヘッダはビッグエンディアンと決まっています (「ネットワークバイトオーダー」と呼びます)。x86 は リトルエンディアンなので、ヘッダを読み書きするたびに変換が要ります。

C の標準では htons() / ntohl() といった関数がありますが、 このプロジェクトは自前の小さな関数を使っています。

rd16be(p)   /* p から 16 ビットをビッグエンディアンとして読む */
wr32be(p,v) /* p へ 32 ビットをビッグエンディアンで書く */
rd32le(p)   /* リトルエンディアン版 */

なぜ両方あるかが重要です。ネットワークのヘッダはビッグエンディアン、 NVMe のコマンドはリトルエンディアンだからです。同じ 1 個のフレームの中で 両方が混在します。取り違えると値が桁違いになります。

6.3 チェックサム — 壊れていないことの確認

IP と TCP のヘッダにはチェックサムという欄があります。 中身を 16 ビットずつ足し合わせた値(の反転)を入れておき、受け取った側が 同じ計算をして一致するかを見ます。

TCP のチェックサムには工夫があり、疑似ヘッダという 実際には送らない仮想的なヘッダも計算に含めます。ここには送信元 IP と宛先 IP が 入ります。こうすると「IP アドレスが化けた」ことも検出できます。

このプロジェクトでは、チェックサムの計算を NIC に任せています (オフロード)。CPU が全バイトを舐めるより速いからです。 ただし「疑似ヘッダの部分和」だけはソフトウェアで計算して種として書き込み、 残りを NIC に埋めさせる、という分担になっています。

実際に踏んだ不具合: ある場面で NIC のオフロードを無効にしたところ、 それまで隠れていたソフトウェア側の計算ミスが表に出ました。 疑似ヘッダの送信元アドレスを間違えていたのですが、NIC が正しい値で 上書きしていたので誰も気付かなかったのです。 「ハードウェアが黙って直してくれる」たぐいの不具合は、 ハードウェアを止めた瞬間に別の場所で出ます。

6.4 MTU — 1 個のフレームに入る大きさの上限

1 個のフレームで運べる中身の大きさには上限があります。これを MTU(Maximum Transmission Unit)と呼びます。 普通の Ethernet では 1500 バイトです。

大きなデータを送るときは、分割して複数のフレームで送ります。 どの層で分割するかで名前が違います。

  • TCP が分割する: 送るバイト列を MTU に収まる大きさに切って送る。 これが普通のやり方です(切れ目のことをセグメントと呼ぶ)。
  • IP が分割する: すでに組み立てたパケットを IP の層で切る。 これがフラグメントです。効率が悪いので避けられます。

このプロジェクトが使うリンクでは、MTU を 9000 バイト超に設定しています (ジャンボフレーム)。1 フレームで多く運べるほど、 1 バイトあたりのヘッダのコストと処理回数が減ります。

境界値の罠: MTU ぴったりのサイズを扱う場所は事故が起きやすいところ です。このプロジェクトでは、IPv6 に対応したときに 「IPv6 ヘッダは IPv4 より 20 バイト長い」ことを忘れて、 フルサイズのフレームだけが NIC に無言で捨てられる、という不具合が ありました。小さいテストデータでは 1 フレームに収まってしまうので 発見できず、テストサイズを大きくして初めて見つかっています。

6.5 このプロジェクトでの受信の入口

フレームが届いてから各層に配られるまでは、こうなっています。

   NIC がフレームを受信して DMA でメモリに書く
              |
              v
   mlx5_net.c : CQ をポーリングして「届いた」を検出
              |
              v
   netif.c    : Ethernet ヘッダを見て、種別ごとに振り分ける
              |
      +-------+--------+---------------+
      v                v               v
   arp.c            ip.c            ipv6.c
   (0x0806)        (0x0800)        (0x86DD)
                      |                |
              +-------+-----+     (同様に分岐)
              v       v     v
           tcp.c   udp.c  icmp.c

0x0806 などの数字は Ethernet ヘッダの中の EtherType という欄の値で、「中身が何か」を示します。

第 7 章 隣の機械を見つける(ARP / NDP)

7.1 なぜ 2 種類のアドレスが要るのか

第 6 章 で、Ethernet ヘッダには MAC アドレス、IP ヘッダには IP アドレスを 書くと説明しました。なぜ 2 つも要るのでしょうか。

  • IP アドレスは「世界のどこか」を指す論理的な番号です。引っ越せば変わります。
  • MAC アドレスは「この機器そのもの」を指す物理的な番号です。工場で焼き 付けられていて変わりません。

送りたい相手の IP アドレスは分かっている。でもフレームを出すには 同じケーブルに繋がっている「次の相手」の MAC アドレスが要ります。 これを調べるのが ARP(IPv4 用)と NDP(IPv6 用)です。

7.2 ARP のやりとり

  A(192.168.101.10)が B(192.168.101.11)へ送りたい

  A → 全員 : 「192.168.101.11 を持っているのは誰? 私は A、MAC は xx:xx」
              (ブロードキャスト = そのケーブルの全員に届く宛先)
  B → A    : 「私です。MAC は yy:yy」(A だけに返す)

  A は (192.168.101.11 → yy:yy) を覚えておく

覚えておく表を ARP キャッシュ と呼びます。 毎回聞いていたら遅いので、一度聞いたらしばらく覚えます。

IPv6 の NDP も考え方は同じですが、ブロードキャストではなく マルチキャスト(特定のグループ宛)を使います。 無関係な機器を起こさない、という改良です。

7.3 キャッシュを永久に持ってはいけない

一度覚えたら永久に使う、では困ります。相手の機器が交換されたら 古い MAC に送り続けてしまいます。そこで有効期限(このプロジェクトの 既定は 60 秒)を設けます。

ただし期限が切れた瞬間に捨てるのも駄目です。 捨ててしまうと、 次にそのアドレスへ送ろうとしたときに「MAC が分からない」状態になり、 送信処理の途中で ARP の問い合わせと応答待ちが発生します。 これは最悪 900 ミリ秒の停止を招きます。

そこで Linux などと同じ 3 段階にしています。

状態条件引いたときの動き
新鮮期限内MAC を返す
古い期限切れ〜猶予期間内MAC を返す + 裏で確認の問い合わせを出す
死亡猶予も過ぎた無効にして「未登録」を返す

「古いけど返す」があるので、送信が止まりません。裏で確認して、 返事があれば期限を延ばし、無ければ次で死亡扱いになります。

7.4 ホットパスに時計を置かない

このキャッシュを引く処理は、TCP のセグメントを 1 個送るたびに通ります。 1 秒に何万回も通る道(ホットパスと呼びます)なので、 無駄な処理を 1 つも置けません。

このプロジェクトでは、次の工夫をしています。

  • 期限は「あと何ミリ秒か」ではなく絶対時刻で持つ。引くときは引き算 1 回 で済み、割り算が要らない(時刻はナノ秒なのでミリ秒に直すと 64 ビット除算 が発生する)。
  • 時刻の読み出しは、アドレスの一致を確認できてから 1 回だけ行う。 一致しないエントリのために時計を読まない。

こういう細かい積み重ねが 第 23 章 の性能に効いてきます。

7.5 到達不能検出(NUD)

「相手がまだ生きているか」を確かめる仕組みを NUD(Neighbor Unreachability Detection)と言います。 RFC 4861 で決められていて、このプロジェクトも実装しています。要点は 4 つです。

  1. 期限切れのエントリを使った瞬間には確認を出さない。 少し待ってから (このプロジェクトでは期限の 1/12)初めて確認する。連続する送信の 1 個目で毎回問い合わせが飛ぶのを避けるためです。
  2. 上位層からの「届いている」証拠を使う。 TCP で「相手が自分のデータを 受け取った」ことが分かったなら、それは問い合わせより強い証拠です。 確認を出さずに期限を延ばします。
  3. 確認はユニキャスト(その相手だけに送る)。MAC を知っている相手に ブロードキャストを撃つ必要はありません。
  4. 偽の応答に騙されない。 「上書きしてよい」という印の無い応答が 既存と違う MAC を主張してきたら無視します。これが無いと、 偽の応答 1 通で他人宛の通信を横取りできてしまいます。

7.6 重複アドレス検出

自分が使おうとしている IP アドレスを、既に誰かが使っていないか確かめる 仕組みもあります。IPv4 では ARP Probe、IPv6 では DAD(Duplicate Address Detection)と呼びます。

やり方は「そのアドレスについて問い合わせを出し、返事が来たら使われている」 です。ポイントは送信元アドレスを空にして出すことで、まだ自分のもので ないアドレスを名乗らないようにします。

このカード特有の問題: このカードはマルチキャストやブロードキャストを 送信元にも返してきます(自分が出したものが自分に戻ってくる)。 重複アドレス検出を入れた途端、各ポートが「自分自身と衝突した」と 報告するようになりました。対策として、送信元 MAC が自分なら応答も 集計もしない、という判定を入れています。

第 8 章 IP — 住所と道案内

8.1 IP の役割

IP(Internet Protocol)の仕事は 2 つです。

  1. 宛先を書く。 世界中で一意な番号(IP アドレス)で相手を指定します。
  2. 道案内をする。 相手が同じケーブル上にいないなら、 「とりあえずこの機械に渡してくれ」という中継役を決めます。

IP アドレスには 2 つの世代があります。

  • IPv4: 32 ビット。192.168.101.11 のように 8 ビットずつ 10 進で書きます。約 43 億個しかなく、枯渇しています。
  • IPv6: 128 ビット。2001:db8:0:1::20 のように 16 ビット ずつ 16 進で書きます。事実上無限です。

このプロジェクトは両方に対応しています。 内部では netaddr_t という 共通の型(種別 + 16 バイトの配列)で持ち回り、ヘッダを組み立てる直前に だけ種別を見て分岐します。

8.2 サブネット — 「同じケーブル上か」の判定

IP アドレスは前半が「ネットワークの番号」、後半が「その中の機械の番号」に 分かれます。どこで分かれるかを示すのがサブネットマスクです。

  自分:       192.168.101.10
  マスク:     255.255.255.0     (前 24 ビットがネットワーク番号)
  ------------------------------------------------
  ネットワーク: 192.168.101.0

  宛先 A: 192.168.101.11  → 前 24 ビットが同じ → 同じケーブル上にいる
  宛先 B: 10.9.9.9        → 違う               → 誰かに中継してもらう

同じケーブル上なら、第 7 章 の ARP で相手の MAC を引いて直接送ります。 違うなら、デフォルトゲートウェイ(中継役のルータ)の MAC を引いて、そこへ送ります。

ここが重要です。

中継してもらうときも、IP ヘッダの宛先は最終目的地のままです。 変わるのは Ethernet ヘッダの宛先 MAC だけです。

  10.9.9.9 へ送りたい(ゲートウェイは 192.168.101.11)

  +----------------------+---------------------+--------
  | Ethernet             | IP                  |
  | 宛先 MAC = ルータの  | 宛先 IP = 10.9.9.9  |  ...
  |            MAC       |          (最終目的地)|
  +----------------------+---------------------+--------

この「次に渡す相手」を次ホップと呼びます。

8.3 断片化(フラグメント)

第 6 章 で MTU の話をしました。IP のパケットが MTU より大きいとき、 IP の層で分割することをフラグメントと言います。

IPv4 のヘッダには、そのための欄があります。

  • 識別子: 同じ元パケットから分かれた断片には同じ番号を振る
  • オフセット: 元のパケットの何バイト目からか
  • MF ビット: 「後にもまだ続く」の印

受け取った側は、識別子でまとめて、オフセット順に並べ直します。

間違えやすい点が 3 つあります。

  1. オフセットは 8 バイト単位で記録されます(13 ビットしかないため)。 したがって最後以外の断片の長さは 8 の倍数でなければなりません。
  2. 全断片で識別子を同じにする必要があります。ヘッダを組み立てる関数が 呼ばれるたびに識別子を増やす作りだと、分割のときに壊れます。
  3. 上位層のヘッダ(TCP など)は先頭の断片にしか入りません。 だから分割は「上位のヘッダまで組み立て終わったあと」に行います。

IPv6 では経路の途中で分割してはいけないことになっています。 送信元が最初から小さく作るか、拡張ヘッダを使って自分で分割します。

このプロジェクトは 送信側の分割も受信側の組み立ても実装済みです。 組み立ては src/ipfrag.c が IPv4 と IPv6 で共通に行います(ヘッダの形が 違うだけで、規則 -- 8 バイト単位のオフセットで並べ直し、識別子でまとめる -- はまったく同じだからです)。

組み立てる側には、送る側には無い危険があります。 断片は他人が好きな 値を書いて送ってくるものなので、そのまま信じて並べるとメモリを壊せます。

  • オフセット + 長さが 65535 を超える断片は捨てます。 捨てないと 用意した領域の外へ書き込みます(古典的な攻撃手法です)。
  • すでに埋まっている場所へは書きません。 どの 8 バイトが到着済みかを ビットの並びで覚えておき、まだ空いている場所だけを埋めます。 こうすると、あとから重なる断片を送りつけて中身をすり替えることが できません。先に届いたほうが勝ちます。
  • 最後でない断片の長さが 8 の倍数でない、オフセットが 8 の倍数でない、 といった規則違反も捨てます。

途中で止まった組み立ては 30 秒で捨てます。 相手が最後の断片を送って こないまま消えたら、いつまでも待つわけにはいきません。この掃除は 次の断片が届いたときに行います。専用の時計を回さないので、 断片が二度と来なければ何のコストもかかりません。

8.4 経路 MTU 探索(PMTUD)

途中の経路に「うちは 1400 バイトまでしか通せない」という区間があると、 それより大きなパケットは通れません。

IPv4 では「分割禁止」の印を立てて送り、通れなかったら中継機が 「大きすぎる。うちの上限は 1400 だ」というエラーを返してきます (第 9 章 の ICMP)。IPv6 も同様のエラーがあります。

これを受け取って宛先ごとに上限を覚えるのが PMTUD(Path MTU Discovery)です。

このプロジェクトの実装では、次の点に注意しています。

  • エラーの中の MTU 値の位置が IPv4 と IPv6 で違います。 IPv4 は 「未使用 4 バイトの後半 2 バイト」、IPv6 は「4 バイト全体」です。 片方のつもりでもう片方を読むと、値が 0 になったり桁が狂ったりします。
  • 学習する宛先は「エラーの送信元」ではなく「元のパケットの宛先」です。 文句を言ってきたルータのアドレスを覚えても意味がありません。
  • 下げる方向にしか動かしません。 学習済みより大きい値の報告は無視します。 そうしないと、偽の大きい値を送り込むだけで学習を無効化できてしまいます。
  • 床を設けます(IPv4 は 576、IPv6 は 1280 バイト)。それ未満は採用しません。

なお、覚えておく表は 第 7 章 の近隣キャッシュとは別に持っています。 近隣キャッシュのキーは「次ホップ」ですが、経路 MTU は「最終宛先」ごとの 性質だからです。同じ表に入れると、同じゲートウェイを通る別々の宛先の値が 混ざってしまいます。

第 9 章 ICMP — 「届かなかった」を伝える

9.1 ICMP の役割

ICMP(Internet Control Message Protocol)は、 ネットワークの都合を伝えるための連絡係です。データを運ぶのではなく、 「届かなかった」「大きすぎる」「生きてますか」といった制御メッセージを扱います。

よく使うものは次の 3 つです。

種別意味使われ方
Echo Request / Reply「生きてる?」「生きてる」ping コマンドの正体
Destination Unreachable「届けられない」相手がいない、ポートが閉じている
Fragmentation Needed「大きすぎる。上限は N」第 8 章 の PMTUD

IPv6 版は ICMPv6 と呼ばれ、番号体系が違います。 また IPv6 では、第 7 章 の NDP も ICMPv6 のメッセージとして 実装されています(IPv4 の ARP が独立していたのとは対照的です)。

9.2 このプロジェクトが返すもの

  • Echo Request が来たら Reply を返します。 だから外部から ping が通ります。
  • 待ち受けていない UDP ポート宛のパケットには「ポート到達不能」を返します。
  • 知らないプロトコル番号には「プロトコル到達不能」を返します。

エラーを返すときは、元のパケットの IP ヘッダと、その先頭 8 バイトを 引用して添えます。受け取った側が「どの通信に対するエラーか」を判断できる ようにするためです。

9.3 実際に起きた問題 — 実装した途端に迷惑をかけた

これは設計を考えるうえで示唆的な事例なので、詳しく書きます。

第 5 章 で、フローステアリングの catch-all のせいで RDMA 用のフレームまで通常の受信キューに複製されて届くという話をしました。 RDMA は UDP の 4791 番ポートを使います。

UDP を実装する前は、これらのフレームは 「未対応プロトコル(17)、無視」というログとして無害に捨てられていました。

ところが UDP を実装した途端、これが「待ち受けていないポート宛の UDP」と 正しく判定されるようになり、RDMA のパケット 1 個ごとに ICMP のエラーを 返し始めました。相手側に大量のエラーが届いて初めて気付きました。

対策は、UDP の 4791 番宛だけは黙って捨てる、という例外です。

教訓: 「今まで黙って捨てていたもの」に処理を付けると、 それまで無害だった異常系が突然表に出ます。 新しいプロトコルを実装したら、既存の機能を一通り動かしてログの差分を 見る必要があります。

第 10 章 TCP — 信頼できるバイトの流れを作る

この章は第 III 部で一番長く、一番重要です。TCP は「信頼できない土台の上に 信頼を作る」仕組みで、そのための工夫がたくさん詰まっています。

10.1 IP は何も保証しない

第 8 章 までの仕組み(IP)は、実は何も保証しません。

  • パケットは失われるかもしれません(混雑した中継機が捨てる)
  • 順番が入れ替わるかもしれません(別の経路を通る)
  • 重複するかもしれません(再送が二重に届く)

その上で「送ったバイト列が、順番どおり、欠けずに、重複せずに届く」ことを 実現するのが TCP です。

10.2 シーケンス番号 — 全バイトに通し番号を振る

TCP の中心的な考え方はこれです。

送るバイト 1 つ 1 つに通し番号を振る。 受け取った側は「ここまで受け取った」を番号で返す。

送る側が付ける番号がシーケンス番号、 受け取った側が返す番号がACK 番号です。

  送信側                            受信側
    |                                 |
    |-- seq=1000, 100 バイト -------->|  (1000〜1099 を受信)
    |                                 |
    |<------------- ack=1100 ---------|  「1100 番から先をください」
    |                                 |
    |-- seq=1100, 100 バイト -------->|

ACK 番号は「次に欲しい番号」です。「1099 まで受け取った」ではなく 「1100 をください」と言います。

もし途中のセグメントが失われると、受信側は同じ ACK 番号を繰り返します。

  送信側                            受信側
    |-- seq=1000 (100 B) ------------>|  OK
    |-- seq=1100 (100 B) --X          |  失われた
    |-- seq=1200 (100 B) ------------>|  1100 が来ていないので…
    |<------------- ack=1100 ---------|  「まだ 1100 が欲しい」
    |-- seq=1300 (100 B) ------------>|
    |<------------- ack=1100 ---------|  「まだ 1100 が欲しい」(重複 ACK)

この重複 ACKが「何かが失われた」の合図になります。

10.3 接続の確立と切断

TCP は「接続」という概念を持ちます。始めるときは 3 回のやりとり (3-way handshake)をします。

  クライアント                     サーバ
      |------- SYN (seq=x) -------->|   「始めたい。私の番号は x から」
      |<-- SYN|ACK (seq=y, ack=x+1)-|   「いいよ。私は y から」
      |------- ACK (ack=y+1) ------>|   「了解」
      |                             |
      |===== 以降データをやりとり ===|

終わるときは、両方向を別々に閉じます。片方が「もう送るものはない」 (FIN)と言っても、逆方向はまだ送れます。

      |------- FIN --------------->|   「私はもう送らない」
      |<------ ACK ----------------|   「了解」(まだ送れる)
      |<------ FIN ----------------|   「私ももう送らない」
      |------- ACK --------------->|   「了解」

閉じたあと、しばらく待つ状態(TIME_WAIT)があります。 遅れて届いた古いパケットが、同じポート番号で始まった次の接続に混ざるのを 防ぐためです。

10.4 ウィンドウ — 相手の受け入れ余地

送る側が一気に大量に送ると、受け取る側のバッファが溢れます。そこで 受信側は「あと何バイト受け取れるか」を毎回 ACK と一緒に伝えます。 これがウィンドウです。

ヘッダのウィンドウ欄は 16 ビットしかない(最大 65535 バイト)ので、 高速なリンクでは足りません。そこでウィンドウスケール というオプションがあり、「この値を 2 の N 乗倍して読んでください」と 接続確立時に取り決めます。

10.5 再送 — 失われたものをどうやって送り直すか

失われたセグメントを送り直す方法は 2 つあります。

(1) 時間切れによる再送(RTO)

送ってから一定時間 ACK が来なかったら送り直します。確実ですが遅い (このプロジェクトの初期値は 500 ミリ秒)。

(2) 重複 ACK による高速再送(Fast Retransmit)

10.2 の重複 ACK が 3 個溜まったら、時間切れを待たずに送り直します。

このプロジェクトは両方を実装しています。ロスを人工的に注入して測ると、 再送の 97% が重複 ACK 由来(時間切れではない)になります。

10.6 実装で分かった 3 つの落とし穴

高速再送を素直に教科書どおり実装すると、このスタックでは発散します。 実測に基づいて 3 つの抑制を入れています。

この節の (1)(2) は、あとで SACK(10.10)を入れたときに 外しました。 どちらも「どこが欠けたか分からない」ことへの対処だった ためです。SACK が使えない相手とつないだときは、いまでもここに書いた とおりに動きます。

(1) 1 個だけ送り直すのではなく、そこから全部送り直す

教科書どおりだと「失われた 1 個だけ」を送り直します。しかし この実装の受信側は順序が乱れたセグメントを 64 個しか保持できません。 1 個ずつ直していると先読みバッファが溢れて二次的な穴が増え、 実測でスループットが 8.99 MB/s まで落ちました。

そこから全部送り直す方式(Go-Back-N)に変えたら 736 MB/s(82 倍)になりました。

(2) 送り直しが生む重複 ACK を差し引く

K 個送り直すと、相手は「もう持ってるよ」という ACK を K 個返します。 これが 3 個以上あると「また失われた」と誤判定して、 再送 → 重複 ACK → 再送の正のフィードバックになります。 実測では破棄 1318 個に対して再送 517,527 回という暴走が起きました。 自分の再送が生む ACK の数を数えて差し引くことで解決しています。

(3) 情報の変わらない ACK を送らない

これは高速再送そのものより効いた発見です。

受信バッファを読み出すたびに「空きが増えました」という ACK を送っていた のですが、広告するウィンドウの値には上限があるため、 実際には値が 1 ビットも変わっていませんでした。相手に伝わる情報は ゼロで、CPU と帯域を捨てていただけです。

さらに悪いことに、この ACK は「重複 ACK」の定義に完全に一致します。 高速再送を入れた直後、ロスが 1 つも無いのに重複 ACK を 419 万個検出し、 10 万回の空振り再送が起きました。

「前回広告した値と同じなら送らない」と直したところ、誤検出が完全にゼロに なり、書き込み性能が 20% 向上しました。

教訓: 「送っても害は無いだろう」で出しているパケットが、 後から入れる機能の判定材料と衝突することがあります。しかも 419 万個という数は、誤検出を追いかけてカウンタを仕込むまで 誰も見ていませんでした。

10.7 閉じたポートへの RST

接続を受け付けていないポートに SYN が届いたら、 RST(リセット)を返して即座に断ります。返さないと、 相手は SYN を 5 回再送して 15.5 秒待ちます。実装したことで 接続失敗の確定が 15.5 秒から 0.2 ミリ秒未満になりました。

ただし RST を返してはいけない場面が 4 つあり、どれを外しても問題が 起きます。

  1. 受信したのが RST のとき。 RST に RST を返すと無限に往復します。
  2. そのポートに待ち受けがいるとき。 待ち受けキュー(10.8)が満杯で 受け取れないだけかもしれません。ここで RST を返すと相手の接続が 即座に失敗します。黙って捨てて再送に任せます(Linux も同じ)。

受け取った RST も、そのまま信じてはいけません。

長らく「4 つ組が一致したら接続を畳む」だけで、番号をまったく見て いませんでした。これだと、前に使っていた接続の遅れて届いた RST が、 いま生きている接続を殺せます(4 つ組は使い回されます)。RFC 5961 は 次のように決めています。

届いた RST の番号どうするか
ちょうど次に期待している番号受け入れて畳む
受け入れ範囲内だが、ずれている確認の ACK を返すだけ(畳まない)
受け入れ範囲の外黙って捨てる

ただし接続を開こうとしている最中(SYN を送った直後)は別扱いです。 受け入れ範囲がまだ決まっていないので、「自分の SYN に対する返事か」で 判断します。ここを分けないと、閉じたポートに繋ぎに行ったときの RST を 弾いてしまい、10.7 の速い失敗が壊れます。

検査するには自分で撃つしかありません。 正しい相手は範囲外の RST を 送ってこないので、rsttest は範囲外の RST を自分で作って撃ち込み、 接続が生き残ること(陰性対照)と、正しい番号の RST では畳まれる こと(陽性対照)を組で確かめます。後者が無いと「そもそも RST を 無視しているだけ」と区別がつきません。

  1. TIME_WAIT の 4 つ組と一致するとき。 閉じた直後に届く遅延パケットを 「閉じたポート宛」と誤判定して、相手の TIME_WAIT を壊してしまいます。
  2. 宛先がマルチキャストのとき。

10.8 待ち受けキュー(backlog)

サーバ側は「接続を待つ」と言っても、いつでも受け取れるわけではありません。 このプログラムのターゲットは、1 本の接続を受け取ったあと、次の受け皿を 用意し直すまでにわずかな間があります。その隙間に SYN が届くとどうなるか、 というのがこの節の話です。

以前は黙って捨てていました。捨てても相手は SYN を再送するので最終的には 繋がりますが、Linux の SYN 再送は 1 回目が 1 秒後なので、接続の確立が まるまる 1 秒遅れます。

そこで待ち受け 1 本につき 4 本ぶんの「待ち行列」を持たせました。 受け皿が用意されていない間に SYN が届いたら、待ち行列の 1 本を使って 先に握手だけ済ませておきます。呼び出し側が受け皿を用意した時点で、 確立済みの接続をそこへ引き渡します。

  相手                    待ち行列                  呼び出し側(nvmet 等)
   |------- SYN --------->|                              |
   |<---- SYN|ACK --------|  ここまでは待ち行列が答える  |
   |------- ACK --------->|  (確立済みで保管)            |
   |                      |                              |
   |                      |<--- 「受け皿を用意した」------|
   |                      |----- 引き渡し --------------->|
   |<==== 以降は普通の接続として続く ====================>|

引き渡しは構造体の複製で行います。 接続 1 本の状態(tcp_conn_t)は 64 バイトの塊で、受信バッファなどの大きな状態は別の表にスロット番号で 繋がっています。だから 64 バイトを複製して、表の指す先を差し替えるだけで、 待ち行列に居る間に届いていたデータも含めてそのまま移せます。

満杯になったら黙って捨てます(RST は返しません。10.7 の 2 番目)。 Linux が accept キュー溢れでそうするのと同じ扱いです。

同時に SYN|ACK の送り直しも入れました。 相手の SYN に SYN|ACK を返した あと、その SYN|ACK が失われると、相手は SYN を再送してきます。以前はこれを 無視していたので、握手が 1 回失敗すると接続は永久に成立しませんでした。

効果は接続の確立時間そのものに出ます。測り方は「最後に繋がったか」 ではなく「何マイクロ秒で繋がったか」です(繋がるだけなら再送でいつかは 繋がるので、退行を検出できません)。自己検査 backlogtest は次を見ます。

条件確立までの時間
待ち行列あり438 マイクロ秒
待ち行列を 0 にする(陰性対照)1.50 秒(SYN を 2 回取りこぼす)
SYN|ACK を 1 個わざと落とす0.50 秒(送り直しで回復)

10.9 タイムスタンプ — 再送中でも往復時間を測る

10.5 の再送は「どれくらい待ってから送り直すか」(RTO)を往復時間から 決めます。ところがその往復時間の測り方には、昔から知られた困りごとが あります。

送り直したセグメントの ACK が返ってきたとき、それは 「1 回目への返事」なのか「2 回目への返事」なのか分かりません。

1 回目だと思って測れば長すぎ、2 回目だと思って測れば短すぎます。 だから伝統的な実装は「再送したぶんは測らない」という安全側の規則 (Karn のアルゴリズム)を使います。このプログラムもそうでした。

副作用があります。ロスが続いている間、往復時間の推定がまったく 更新されなくなるのです。いちばん知りたい場面で、いちばん情報が 止まります。

タイムスタンプ(RFC 7323)はこれを直します。送る側が セグメントに時刻を書き、受け取った側がその値をそのまま返します。返ってきた 値を今の時刻から引けば往復時間です。どちらの送信への返事かは書いてある 値そのものが教えてくれるので、再送していても測れます。

  送信側                                  受信側
    |-- seq=1000  TSval=500  ------------>|
    |<------------ ack=1100  TSecr=500 ---|   「500 と書いてあったよ」
    |
    |  いまが 512 なら、往復時間は 12

実測(わざと 12 個に 1 個のセグメントを捨てた状態で 512KB を流す):

往復時間の更新回数再送
タイムスタンプあり25 回6
なし(陰性対照)14 回12

もう 1 つの役目が PAWS です。シーケンス番号は 32 ビットなので、 速いリンクでは一周してしまいます。このプログラムの実効速度でも一周は 約 5 秒で、閉じた接続を覚えておく時間(4 秒)と大差ありません。 一周した古いパケットを新しいものと取り違える危険があるところを、 「時刻が巻き戻っているものは捨てる」ことで防ぎます。

代償は 1 セグメントあたり 12 バイトです。オプションを載せたぶんだけ 運べるデータが減るので、送る側が自分で 12 引きます(RFC 6691)。 実測では自作側も Linux 側も 9216 − 12 = 9204 に落ち着きました。 両者が独立に同じ値を出していることが、合意できている証拠になります。

ここで 1 つ壁に当たりました。 第 5 章の LSO(ヘッダを 1 つ 渡して分割を NIC に任せる仕組み)は、ヘッダをカードの命令の中へ 丸ごと書き写します。命令の大きさに上限があるので、ヘッダが長いと 入りません。IPv4 では入りますが、IPv6 + タイムスタンプ(86 バイト)は 上限(82 バイト)を超えます。その組み合わせだけ LSO を使わず 1 つずつ 送るようにしました。「速くする仕組み」には、こういう見えない上限が あります。

10.10 SACK — 「どこが欠けたか」を正確に伝える

10.6 で見たとおり、この実装の再送は長らく Go-Back-N (失われた地点から先を全部送り直す)でした。相手は「1100 が欲しい」としか 言えないので、1100 の先が届いているかどうか送り手には分からないからです。

SACK(選択確認応答、RFC 2018)はここを変えます。 受け取った側が「1100 は無いけど 1200〜1299 は届いている」と、 とびとびの区間をそのまま伝えます。

  送信側                              受信側
    |-- 1000 --------------->|   OK
    |-- 1100 -----X          |   失われた
    |-- 1200 --------------->|
    |<-- ack=1100, SACK 1200〜1299 ---|   「1100 が欲しい。1200〜1299 は有る」
    |
    |-- 1100 だけ送り直す --->|   ← Go-Back-N なら 1200 以降も送り直していた

送り直す量が減るだけでなく、送り直さない範囲を決められるのが重要です。 一番先の SACK 区間より先は「まだ飛んでいる途中」なので、送り直す必要が ありません。

実測(わざとロスを注入した NVMe/TCP):

書き込み読み出し時間切れ待ちの再送ロス 1 個あたり送り直したセグメント
SACK あり525 MiB/s501 MiB/s2 回23.8
なし(Go-Back-N)364 MiB/s328 MiB/s36 回72.1

ロスが無いときは 1 バイトも速くなりません(送り直しが起きないので)。

実装しただけでは 1 バイトも速くなりませんでした。 効果が出るまでに 5 か所直しています。いちばん大きかったのは 「途中まで届いた」という知らせが来るたびに次の穴を送り直すことで、 これを入れる前後で読み出しが 106 → 614 MiB/s、時間切れ待ちの再送が 39 → 0 になりました。詳しくは PLAN_protocol_gaps.md の段階 25 に 全部書いてあります。

途中で「SACK にしたら 3 倍遅い」という状態にもなりました。 そのとき 役に立ったのが、「やりとりはするが送り直し方だけ元に戻す」モード (tcpsack report)を作って測ったことです。3 つ並べると 106 / 407 / 464 MiB/s となり、やりとり自体はタダで、悪いのは 送り直し方だと一目で分かりました。「新しい機能が遅い」ときは、 その機能のどの部分が原因かを切り替えられる形にして測るのが近道です。

相手が Linux のときが本番です。 Linux は SACK を既定で使うので、 わざとロスを起こしながら 32MiB を書いて読み戻すと、Linux が送ってきた 区間の知らせを 20 回受け取り、60 個ぶんの送り直しを省略しました。 読み戻した 32MiB は 1 バイトも違いませんでした。

10.11 キープアライブ — 黙って消えた相手を見つける

TCP は何もやりとりしていない接続を勝手に切りません。そのため、相手が 電源ごと消えた(ケーブルが抜けた、クラッシュした)場合、こちらは 永遠に待ち続けます。

キープアライブ(RFC 1122 4.2.3.6)はこれを防ぎます。 一定時間なにも届かなくなったら、わざと「1 つ前の番号」を付けた空の セグメントを送ります。相手が生きていれば、既に受け取った番号なので 「もう持っています」という ACK が必ず返ってきます。

  こちら                              相手
    |  (2 時間なにも届かない)          |
    |-- seq = 次に送る番号 - 1、データ無し -->|
    |<------------- ack ---------------|   生きていれば必ず返る

返ってこなければ間隔をあけて繰り返し、決めた回数で接続を畳みます。 既定は慣例どおり 2 時間 + 75 秒 × 9 回です。短くしたくなりますが、 短くすると「話していないだけで生きている」正常な接続を切ってしまいます。

こちらが相手の問い合わせに答えていませんでした。 実装していて 見つかった既存の穴です。ACK を返すのは「データを運ぶセグメント」と 切断要求のときだけで、空のセグメントは黙殺していました。 Linux はキープアライブを既定で使うので、相手から見るとこちらが 死んでいるように見え、接続を切られます。

検証は Linux のカーネルに判定させました。 Pi5 から 「1 秒で問い合わせ、1 秒間隔、3 回で諦める」設定で接続し、12 秒放置します。

向き結果
Linux → こちら12 秒間つながったまま(こちらは 11 回応答した)。直す前なら 4 秒ほどで切られていた
こちら → Linux設定を縮めて 11 回問い合わせ、切断ゼロ(Linux が答えている)

自己検査 keepalivetest は、応答を落とすと畳まれる(陽性対照)と 応答があれば畳まれない(陰性対照)を組で確かめます。前者だけでは 「ただの時間切れ」と区別がつきません。

第 11 章 UDP と IPv6

11.1 UDP — 何も保証しない代わりに軽い

UDP(User Datagram Protocol)は、TCP と対照的に何も保証 しません。順番も、到達も、重複しないことも。ヘッダはたった 8 バイトです。

 +--------+--------+--------+--------+
 | 送信元ポート    | 宛先ポート      |
 +--------+--------+--------+--------+
 | 長さ            | チェックサム    |
 +--------+--------+--------+--------+

このプロジェクトで UDP が要る理由は 2 つあります。

  1. RoCEv2(RDMA)が UDP の上に載っている(第 15 章)
  2. 動作確認用

チェックサムについて 1 点だけ注意があります。計算結果がたまたま 0 に なったときは、0 ではなく 0xFFFF を書きます。UDP では 0 が 「チェックサム無し」を意味するからです。

11.2 IPv6 で追加されること

IPv6 は「IPv4 のアドレスを長くしただけ」ではありません。付随する仕組みが いくつかあります。このプロジェクトはそれらも実装しています。

(1) リンクローカルアドレス

fe80:: で始まるアドレスで、MAC アドレスから自動的に作られます。 設定なしで同じケーブル上の通信ができます。

(2) SLAAC(アドレスの自動設定)

ルータに「このネットワークの番号は何ですか」と尋ね(RS)、 返ってきた答え(RA)と自分の MAC を組み合わせて、 世界で通用するアドレスを自分で作ります。DHCP のような サーバが要りません。

(3) MLD(マルチキャストの参加表明)

「私はこのマルチキャストグループを聞いています」とスイッチに伝えます。 賢いスイッチは、聞いている人がいないマルチキャストを転送しません。 つまり MLD を実装しないと、そういうスイッチの配下では 第 7 章 の NDP が一切通りません(NDP はマルチキャストを使うため)。

(4) 拡張ヘッダ

IPv6 では、オプション的な情報を「基本ヘッダと上位プロトコルの間に挟む」 形で表します。数珠つなぎになっていて、順に辿る必要があります。

 +----------+------------+-----------+--------------+
 | IPv6     | Hop-by-Hop | Fragment  | TCP ...      |
 | (next=0) | (next=44)  | (next=6)  |              |
 +----------+------------+-----------+--------------+
      └── 次は何か ─┘ └── 次は何か ─┘

辿るときの注意点が 4 つあります。

  • 長さの単位は「(記載値 + 1) × 8 バイト」(最初の 8 バイトを含まない)
  • Hop-by-Hop の中の項目は {種別, 長さ, 値} の並びだが、 種別 0(パディング 1 バイト)だけは長さの欄を持たない。 一律に読むとそこからずれます。
  • 知らない項目に出会ったときの扱いは、種別の上位 2 ビットが決めます。 「無視してよい」以外は捨てなければなりません。
  • 上位プロトコルの長さは、全体長から拡張ヘッダぶんを引く必要があります。 忘れるとチェックサムの検証が全部壊れます。

Fragment(種別 44)だけは辿って終わりにできません。 これが挟まって いるということは、そこから先が元のパケットの一部でしかないという意味 だからです。辿る側はここで止めて、組み立てる側(第 8 章 8.3)へ 渡します。全部そろってから、Fragment ヘッダが持っていた「本当の次は何か」 を使って上位へ渡し直します。

11.3 IPv6 対応で実際に踏んだ不具合

外部の Linux 機と繋いで初めて見つかったものが 3 件あります。いずれも 自作どうしで通信している限り、両側が同じ間違い方をするので絶対に 検出できない性質のものでした。

  1. マルチキャストの受信が無効だった。 NDP の問い合わせはマルチキャスト で来るので、NIC のフィルタに弾かれて外部からの IPv6 が 1 フレームも 受け取れませんでした。IPv4 の ARP はブロードキャストなので通っていて、 それで気付きませんでした。
  2. メッセージ中のアドレスの位置が 4 バイトずれていた。 送る側も受け取る側も同じだけずれているので、自作どうしでは全部通ります。
  3. 応答に常に自分のリンクローカルアドレスを入れていた。 相手が 「聞いたのと違うアドレスだ」と判断して捨てます。リンクローカル宛の ping6 だけ通り、グローバルアドレス宛が通らない、という形で出ました。

教訓: 正規の実装と繋ぐまで、自作どうしの検証では見つからない 種類の不具合があります。 第 29 章 で、この教訓から生まれた 検証手法を説明します。

11.4 HW オフロードは IPv6 でもそのまま使える

実装時、第 6 章 で触れたチェックサムのオフロードと、 大きなデータを NIC に分割させる機能(LSO、第 23 章)を、 「NIC は IPv4 前提だろう」と考えて IPv6 では無効にしていました。

実測したら両方ともそのまま動きました。 無効にしていた間は、 IPv4 と比べて書き込みが 38%、読み出しが 47% 遅くなっていました。

教訓: 「ハードウェアの機能は古い規格前提だろう」という推測で 機能を切ると、動くはずのものを落としたまま気付きません。 切る前に一度有効にして測るべきです。

第 12 章 NVMe の考え方

12.1 SSD との会話はキューで行う

昔のハードディスクとの会話は「命令を 1 個送って、終わるまで待つ」形でした。 機械が回転して磁気ヘッドが動くのを待つので、それで十分だったのです。

SSD は機械的な待ち時間が無く、しかも内部で何十もの処理を同時に進め られます。1 個ずつ待っていては性能が出ません。そこで NVMe は、 第 5 章 で見たのと同じキューの考え方を採用しました。

   ホスト(PC)                              SSD
   +---------------------+
   | 送信キュー(SQ)    |  ← ここにコマンドを積む
   |  [cmd][cmd][cmd]... |  → SSD が読みに来る(DMA)
   +---------------------+
   +---------------------+
   | 完了キュー(CQ)    |  ← SSD が結果を書き込む(DMA)
   |  [結果][結果]...    |  → ホストが読む
   +---------------------+

コマンドを積むだけ積んで、結果は後でまとめて回収します。 これが 「キュー深度」(同時に何個投げっぱなしにするか)という 概念の正体です。第 1 章 のベンチマーク出力にあった qd がこれです。

12.2 コマンドと完了の形

NVMe のコマンドは 64 バイト固定です(SQE、 Submission Queue Entry と呼びます)。

  バイト  0     : オペコード(何をするか。読み=0x02、書き=0x01 など)
  バイト  2-3   : コマンド ID(この命令を識別する番号)
  バイト  4-7   : 名前空間 ID(どの領域か。次節)
  バイト 24-39  : データの置き場所
  バイト 40-43  : cdw10  ┐
  バイト 44-47  : cdw11  │ コマンドごとに意味が違う 6 個の 32 ビット欄
       …                 │ (cdw = Command Dword)
  バイト 60-63  : cdw15  ┘

完了は 16 バイト固定です(CQE、Completion Queue Entry)。

  バイト  0-3   : 結果の値(コマンドによる)
  バイト  8-9   : キューの進み具合
  バイト 12-13  : どのコマンド ID に対する完了か
  バイト 14-15  : ステータス(成功か、失敗ならその理由)

同じ「CQE」という略語が 第 5 章 の NIC のところにも出てきました が、別物です。 NIC の CQE は「送信が終わった」、NVMe の CQE は 「読み書きが終わった」を表します。文脈で区別してください。

12.3 名前空間 — SSD の中の区画

1 台の SSD を複数の領域に分けて使えます。この 1 つ 1 つを 名前空間(Namespace)と呼び、nsid という番号で 指定します。Linux からは /dev/nvme0n1、/dev/nvme0n2 のように見えます。

各名前空間は「LBA(Logical Block Address、論理ブロック番号)が 0 から N まである」という形で表されます。1 ブロックの大きさは典型的には 512 バイトか 4096 バイトです。

このプロジェクトは名前空間を 2 つ持っています。 1 番が 256 メガバイト、 2 番が 32 メガバイトです(実体はメモリ上の配列)。大きさを変えてあるのは メモリの節約のためでもありますが、「名前空間ごとに別の領域を見ているか」 の検証としても効くからです(第 29 章)。

12.4 admin キューと IO キュー

キューには 2 種類あります。

  • admin キュー: 管理用。「あなたは誰ですか」 (Identify)、「設定を変えたい」(Set Features)といった制御を行います。 接続ごとに 1 本だけです。
  • IO キュー: 実際の読み書き用。何本でも作れます (普通は CPU コアの数だけ)。

このプロジェクトは IO キューを 1 本だけ作ります。

12.6 非同期イベント要求という変わったコマンド

Async Event Request(AER)は独特です。 ホストが先に投げておいて、コントローラは何か起きるまで完了させません。

  ホスト → 「何かあったら教えて」(AER を投げる)
                  … 何時間でも待つ …
  コントローラ → 「名前空間が増えました」(このとき初めて完了を返す)
  ホスト → 「了解」+ すぐに次の AER を投げる

普通のコマンドは「投げたらすぐ返ってくる」ものなので、ここで即座に 成功を返してしまうと、ホストが即座に再発行して無限ループになります。

13.1 発想の転換

13.2 Fabrics コマンド

ネットワーク越しになると、PCIe には無かった手順が要ります。

  • 接続の確立: 「これからあなたに繋ぎます」という挨拶
  • 相手の識別: PCIe なら「このスロットの装置」で分かりましたが、 ネットワークでは名前が要ります

そのために Fabrics コマンド(オペコード 0x7F)という 特別な系統が追加されています。中でも重要なのが Connect です。

Connect のときにホストが渡すもの:

  • NQN(NVMe Qualified Name): 繋ぎたい相手の名前。 nqn.2014-08.org.nvmexpress:uuid:... のような長い文字列です。
  • キュー ID: 0 なら admin キュー、1 以上なら IO キュー
  • KATO(Keep Alive Timeout): 「この時間コマンドが 来なかったら私が死んだと思ってください」

13.3 Discovery — 何が繋がっているかを尋ねる

いきなり NQN が分かっているとは限りません。そこで、 「ここには何がありますか」と尋ねるための特別なコントローラが 定義されています。Discovery コントローラと呼び、 NQN は nqn.2014-08.org.nvmexpress.discovery で固定です。

$ sudo nvme discover -t tcp -a 192.168.101.11 -s 4421
Discovery Log Number of Records 1
=====Discovery Log Entry 0======
trtype:  tcp
subnqn:  nqn.2014-08.org.nvmexpress:uuid:deadbeef-...
traddr:  192.168.101.11

このプロジェクトも Discovery に対応しています。

実装時に踏んだ問題: Discovery は IO キューを作りません。 通常の接続を前提に「IO キューの後始末係が接続の終了を検出する」構造に なっていたため、Discovery のあと誰も後始末をせず、以後この待ち受けが 一切の接続を受け付けなくなるという不具合がありました。

教訓: 後始末を別の担当に任せている構造では、 その担当が動かない経路を足したときに後始末が誰の仕事でもなくなります。

第 14 章 NVMe/TCP

14.1 PDU — TCP の上に区切りを作る

TCP はバイトの流れです。区切りがありません。一方 NVMe のコマンドは 64 バイトの塊です。だから「ここからここまでが 1 個のコマンド」という 区切りを自分で作る必要があります。

その単位が PDU(Protocol Data Unit)です。

 +--------------------------------+
 | 共通ヘッダ(8 バイト)         |
 |   種別 / フラグ / ヘッダ長 /   |
 |   データ開始位置 / 全体長      |
 +--------------------------------+
 | 種別ごとの部分                 |
 +--------------------------------+
 | (ヘッダのチェック値)         |
 +--------------------------------+
 | データ                         |
 +--------------------------------+
 | (データのチェック値)         |
 +--------------------------------+

全体長がヘッダに書いてあるので、受け取る側は「あと何バイト読めば 1 個ぶんか」が分かります。

主な種別:

0x04CapsuleCmdホスト→NVMe コマンド(64 バイト)を運ぶ
0x05CapsuleResp→ホスト完了(16 バイト)を運ぶ
0x06H2CDataホスト→ホストからのデータ本体
0x07C2HData→ホストターゲットからのデータ本体
0x09R2T→ホスト「データを送ってください」

14.2 データの運び方が 2 通りある

書き込みのとき、データをどう運ぶかに 2 つの方式があります。

(1) in-capsule(カプセル同梱)

コマンドの PDU にデータをくっつけて 1 回で送ります。

  +-----------+------------------+---------------+
  | PDU ヘッダ | NVMe コマンド    | データ         |
  +-----------+------------------+---------------+

やりとりが 1 往復で済むので速いのですが、大きなデータには向きません。 上限は接続時に取り決めます。

(2) R2T(Ready To Transfer)

コマンドだけ先に送り、ターゲットが「準備できたので送ってください」 (R2T)と返してから、データを送ります。

  ホスト → CapsuleCmd(「書け」だけ)
  ホスト ← R2T       (「0 バイト目から 64KB 送って」)
  ホスト → H2CData   (データ)
  ホスト ← CapsuleResp(完了)

やりとりが増える代わりに、ターゲットが受け入れ量を制御できます。

読み出しは単純で、ターゲットが C2HData でデータを送り、 最後に完了を返します(完了をデータの PDU に埋め込む省略形もあります)。

14.3 ダイジェスト(CRC32C)

TCP にもチェックサムはありますが、16 ビットしかなく強度が低いため、 NVMe/TCP は独自に CRC32C という 32 ビットの検査値を 付けられます。ヘッダ用(HDGST)とデータ用(DDGST)があり、 接続時に使うかどうかを取り決めます。

このプロジェクトは両方に対応しています。CRC32C の計算は x86 の専用命令(SSE 4.2 の crc32)を使い、さらに 3 本の計算を 交互に回して並列度を上げています(第 23 章)。

この実装で 3 回踏んだ不具合(いずれも同じ形):

1. CRC の最後の反転を忘れる 2. ヘッダの長さを確定させる前にヘッダのチェック値を計算する 3. 2 を直したとき、長さだけ直してフラグの欄を見落とし、同じ形で再発

どれも「自分の検証は通るのに、相手側だけが静かに接続を切る」という 非対称な症状になります。ヘッダのどの欄も、チェック値を計算する前に 最終値にしておく必要があります。

14.4 「もう続けられません」を伝える

チェック値が合わなかったときのような致命的な誤りを見つけたら、 NVMe/TCP では接続を閉じる前に理由を伝える PDU(Terminate Connection Request)を送る決まりです。送らずに切ると、相手のログには 「接続が切れた」としか残りません。

長らく種別の定義だけがあって、送りも受けもしていませんでした。 いまは、致命的な誤りを見つけたら理由の番号(FES)を添えて送り、 相手から届いたら記録して畳みます。

ヘッダのチェック値が合わなかったときの扱いも変えました。 以前は 「読み直して同期を取り直す」でしたが、ヘッダが壊れている以上、 次の PDU がどこから始まるのか分かりません。読み直しても、ずれた ところを読み続けるだけです。いまは致命的な誤りとして畳みます。

検査は Linux のカーネルに読ませました。 こちらのチェック値の判定を わざと失敗させると、こちらが理由つきの PDU を送り、Linux がこう記録します。

nvme nvme0: Received C2HTermReq (FES = Header Digest Error)

理由の番号を Linux が文字列に解釈しているので、PDU の並びも番号も 合っていると言えます。

なぜ「判定をわざと失敗させる」必要があるのか。 送る側を壊すと、 Linux は誤りを検出しますが理由の PDU を送り返してはくれません (Linux のホストは黙って畳む実装)。こちらが送る側の経路を試すには、 こちらが「壊れている」と判定しなければならない、という理屈です。

第 15 章 RDMA と RoCEv2

15.1 RDMA とは何か

第 14 章 の NVMe/TCP では、データが届くたびに受け取る側の CPU が 働きます。TCP の処理をして、PDU を解析して、メモリにコピーして…。

RDMA(Remote Direct Memory Access)は、これを 相手の CPU を働かせずに行います。

   通常(TCP):
     送信側 CPU → NIC → …… → NIC → 受信側 CPU → メモリ
                                     ↑ ここで CPU が働く

   RDMA:
     送信側 CPU → NIC → …… → NIC → メモリ
                                     ↑ CPU を通らない

受信側の NIC が、あらかじめ許可された領域に直接書き込みます。 第 5 章 で説明した MKey(メモリの使用許可証)が ここで効いてきます。

15.2 RDMA の操作

操作意味
SEND普通の送信。相手の受信キューに入る(相手の CPU が気付く)
RDMA_WRITE相手のメモリに直接書く(相手の CPU は気付かない)
RDMA_READ相手のメモリから直接読む(相手の CPU は気付かない)

RDMA_WRITE / READ をするには、相手のメモリの アドレスと鍵(rkey)を知っている必要があります。 これは事前に SEND などで教え合います。

15.3 なぜ「書き込み」が RDMA_READ になるのか

ここが直観に反するところです。

NVMe-oF RDMA では、ホストがデータを「書く」とき、 ターゲットがホストのメモリから RDMA_READ で引き込みます。

  ホスト → 「書け。データは私のメモリのここ(アドレスと鍵)にある」
  ターゲット → RDMA_READ でホストのメモリを読む
  ターゲット → 「終わった」

ホストが押し込むのではなく、ターゲットが引き取りに行くわけです。 こうするとターゲットが受け入れ速度を制御できます。

この構造には重要な性能上の意味があります。

同時に投げられる RDMA_READ の本数が、そのまま書き込み性能の上限に なります。 読み出し(ターゲットが RDMA_WRITE で押し込む)は この制限を受けません。

このプロジェクトでは、この設定に2 件の不具合がありました。

  1. カードの能力値を読むビット位置が 4 ビットずれていたため、 「同時 1 本」と誤認していた(本当は 16 本)。
  2. 設定を書き込む QP の状態遷移が間違っていた (第 5 章 5.8 で触れた話)。1 だけ直すと、相手が 2 本目を 投げた瞬間にエラーになりました。

両方を直した結果、書き込み性能が 2.3 倍になりました。 「書き込みだけがキュー深度でスケールしない」という症状が出たら、 まずここを疑うべきです。

15.4 RoCEv2 — Ethernet の上で RDMA をやる

RDMA はもともと InfiniBand という専用のネットワーク規格のものでした。 これを普通の Ethernet + IP + UDP の上で動かすのが RoCEv2(RDMA over Converged Ethernet version 2)です。

 +----------+------+-------+---------+------------------+
 | Ethernet |  IP  | UDP   | IB の   | RDMA のデータ    |
 |          |      | 4791番| ヘッダ  |                  |
 +----------+------+-------+---------+------------------+

UDP の 4791 番ポートを使います(第 11 章 で触れた番号です)。

接続の確立には CM(Connection Manager)という手順を使います。 REQ → REP → RTU の 3 段階で、TCP の 3-way handshake に似ています。

15.6 なぜ同じカードの 2 ポート間で通らないのか

このプロジェクトは 第 1 章 の図のとおり、 1 枚のカードの 2 つのポートを使って自分自身と通信します。 ところが RoCEv2 だけはこれができません。

切り分けた結果は次のとおりです。

宛先ワイヤに出るか
Pi5(別の機械)の MAC + Pi5 の IP出る
Pi5 の MAC + 自分のもう一方のポートの IP出ない
自分のもう一方のポートの MAC + 存在しない IP出ない

つまり 宛先の MAC か IP のどちらかが自分の装置のものだと、 カードのファームウェアが内部で処理しようとして消えます。

対策を探して、次のことを試しました(すべて効果なし)。

  • ファームウェアの設定項目(MPFS_UC_LOOPBACK_DISABLE)→ このカードは非対応
  • 内部折り返しを無効にする設定ビット → 読み戻して立っていることを 確認したうえで、症状は変わらず
  • 送信側のフローステアリングで強制的に外へ出す → 「外へ出す」という 宛先指定がそもそも存在しない

そして決定的なのは、Linux 純正のドライバでも同じように失敗することです。 ネットワーク名前空間で 2 つのポートを分離して標準ツールで試しても、 RDMA のデータが 1 バイトも流れません。つまりこれは自作ドライバの不具合 ではなく、このカードの制約です。

15.7 では何が未確認なのか

上のとおり RoCEv2 のパケットは Pi5 との間で往復できています。 しかし NVMe-oF RDMA としてのエンドツーエンド、つまり

自作のイニシエータ → Pi5 の Linux が動かす NVMe-oF RDMA ターゲット へ接続して、実際に読み書きする

はまだ実施していません。理由は、bench コマンドが接続先を 指定できる形になっていない(同じカードの 2 ポート間を前提にしている) ためです。これは残作業です。

過去には動いていました。 100 ギガビットの別のカードを使い、 2 つのポートを直結していた時期には、NVMe-oF RDMA のベンチマークが完走 していました。README.md の性能表にある RDMA の数値はそのときのものです。 ただしその構成でも、フレームがワイヤを通っていたのか内部で折り返して いたのかは区別できていませんでした(区別する手段が無かったため)。

15.8 未検証のまま残っている実装

RoCEv2 が現構成で動かせないため、ターゲット側の RDMA 実装 (nvmet_rdma.c)には、TCP 側に入れた切断処理の改善が入っていません。

16.3 切断の作法 — 相手の手順に合わせる

自作どうしで通信している限り絶対に見つからない不具合の代表例です。

Linux は接続を閉じるとき、次の順で畳みます。

  ① IO キューを切る
  ② admin キューに「シャットダウンします」と書く(CC.SHN)
  ③ その状態が反映されるのを待つ(CSTS.SHST を最大 5 秒ポーリング)
  ④ admin キューを切る

このプロジェクトは当初、①を見た時点で admin キューも閉じていました。 自作のイニシエータは①のあと②をしないので、それで問題なかったのです。

Linux と繋いだ結果:

  • ②が無応答になり、ホスト側で60 秒のコマンドタイムアウト
  • ③の状態を返していなかったので、毎回 5 秒待たされる

両方を直して、切断にかかる時間が 61 秒から 1 秒未満になりました。

教訓: 「相手も自分と同じ手順で喋る」という前提は、 切断のような「成功パス以外」にこそ残っています。

16.4 状態を持つと後始末が要る

Keep Alive のタイマを実装したときに、既存の不具合が表に出ました。

それまで接続の畳み方は「IO キューが先に終わる → admin が待つ」の 1 通り しかありませんでした。ところが Keep Alive の時間切れでは admin が先に畳みます。すると、あとから IO 側が立てる「終わりました」の 旗を、admin が次の接続のものと誤解して、10 秒後に正常な接続を 畳んでしまいました。

教訓: 後始末を 2 つの担当が旗で伝え合う構造は、 畳む順序が変わると壊れます。 新しい「畳む契機」を足したら、 既存の旗が逆の順序でも成立するかを確認する必要があります。

16.5 0's based という落とし穴

NVMe では、多くの個数の欄が 「0 が 1 個を意味する」(0's based)形式です。 「16 個」なら 15 と書きます。

ところが全部がそうではありません。

欄0's based か
Write Zeroes の「ブロック数」そう(+1 する)
Dataset Management の「範囲の個数」そう(+1 する)
Dataset Management の各範囲の「ブロック数」違う(そのまま)

この取り違えは、バイト配置を検算する道具では見つかりません (値の解釈の問題だから)。実際のデータで 「8 ブロックだけ消えて 9 ブロック目が残っている」ことを確かめる 必要があります。

(2) nic_ops_t(NIC の抽象)

  1. 元がベアメタル環境だった。ヒープが無い。
  2. DMA できるメモリは特別(第 3 章)。どこに置かれるかを 制御したい。

第 18 章 協調ジョブスケジューラ

18.1 なぜスレッドを使わないのか

「TCP の接続を処理する」「NVMe のコマンドを待つ」といった仕事を同時に 進める必要があります。普通ならスレッドを使うところです。

このプロジェクトはスレッドを使わず、協調マルチタスクを 使っています。理由は次のとおりです。

  • ロックが要らない。 スレッドだと共有データにロックが必要ですが、 ロックはホットパスでは高価です。
  • 切り替えのコストがゼロ。 関数を呼ぶだけです。
  • 元がベアメタル環境だった。スレッドの仕組みが無い。
  • ポーリング前提の設計と相性が良い。 どうせ CPU を回し続けるので、その中で順番に見て回れば済みます。

18.2 ジョブとは「1 tick 進むステートマシン」

ジョブは、次の形の関数です。

static job_result_t my_job_step(job_t *self)
{
    switch (self->state) {
    case ST_A:
        /* 少しだけ進める。待つ必要があれば、そのまま返る */
        if (まだ条件が揃っていない) return JOB_WAITING;
        self->state = ST_B;
        return JOB_WAITING;

    case ST_B:
        ...
        return JOB_DONE;   /* 完了。スケジューラから外れる */
    }
}

大事な約束は「ブロックしないこと」です。この関数の中で待ち続けると、 他のジョブが一切動けなくなります。「まだ来ていない」なら JOB_WAITING を返して、次の tick でまた呼ばれるのを待ちます。

スケジューラ本体はとても単純です。

void job_scheduler_tick(void) {
    for (各ジョブ) {
        if (このコアが担当するジョブなら)
            結果 = job->step(job);
        if (結果 == JOB_DONE) ジョブを外す;
    }
}

これを無限ループで回します。同時に走れるジョブの上限は 12 個です。

18.3 何がジョブになっているか

  • NVMe-oF ターゲットの admin キュー担当
  • NVMe-oF ターゲットの IO キュー担当
  • NVMe-oF イニシエータの接続担当
  • RDMA の接続管理(CM)担当

たとえばターゲットの admin キューのジョブは、次のような状態を持ちます。

  ARM(待ち受けを張る)
    → ACCEPT_WAIT(接続を待つ)
    → ICREQ_RECV(初期化要求を受け取る)
    → ICRESP_SEND(応答を返す)
    → RECV_HDR ⇄ (コマンドを受け取って処理する、をずっと繰り返す)
    → (切断されたら ARM へ戻る)

「終わったら次のクライアントを待つ」ので、サーバのジョブは JOB_DONE をほとんど返しません。

18.4 この構造の弱点

1 つのジョブが長時間 CPU を占有すると、他が止まります。

たとえば「32 メガバイトをゼロで埋める」という命令 (第 16 章 の Write Zeroes)は、実行に数ミリ秒かかります。 その間、他のジョブは動きません。TCP の応答が数ミリ秒遅れます。

このプロジェクトはこれを許容していますが、上限を設けるという対処を しています。ホストに「1 回の命令で消せるのは 32 メガバイトまでです」と 広告することで、それより大きな要求が来ないようにしています。

18.5 ジョブの後始末は難しい

実際に起きた問題を記録しておきます。

RDMA の接続に失敗したとき、失敗を検出したジョブだけが止まって、 関連する別のジョブが動き続けていました。そこへ別のコアが 「使っていたデータ構造をゼロクリア」したため、動き続けていたジョブが NULL ポインタを踏んで落ちました。

この経験から、job.c には次の関数が用意されています。

unsigned job_cancel_by_ctx(const void *ctx);  /* このデータを使うジョブを止めて */
unsigned job_count_by_ctx(const void *ctx);   /* まだ何個残っている? */

約束: ジョブが使っているデータ構造を作り直す前に、 それを参照しているジョブが 0 個になるまで待つこと。

第 19 章 主要なデータ構造

19.1 tcp_conn_t — TCP の接続 1 本

この構造体はちょうど 64 バイトで、キャッシュライン 1 本に収まるよう設計されています。

typedef struct __attribute__((aligned(64))) {
    volatile tcp_state_t state;        /*  0: 4  状態(ESTABLISHED など)*/
    volatile uint16_t    local_port;   /*  4: 2 */
    volatile uint16_t    remote_port;  /*  6: 2 */
    volatile uint32_t    snd_seq;      /*  8: 4  次に送る番号 */
    volatile uint32_t    rcv_seq;      /* 12: 4  次に期待する番号 */
    volatile uint32_t    snd_win;      /* 16: 4  相手の受け入れ余地 */
    volatile uint16_t    snd_mss;      /* 20: 2  1 個の最大サイズ */
    uint8_t              pad0[2];      /* 22: 2 */
    volatile unsigned    owner_core;   /* 24: 4  担当コア */
    netaddr_t            local_ip;     /* 28:17 */
    netaddr_t            remote_ip;    /* 45:17 */
    uint8_t              pad1[2];      /* 62: 2 */
} tcp_conn_t;

_Static_assert(sizeof(tcp_conn_t) == 64, "1 キャッシュラインちょうどに収める");

注目してほしいのは 3 点です。

  1. _Static_assert でサイズを固定している。 フィールドを足して 64 バイトを超えたらビルドが失敗します。うっかり性能を落とせません。
  2. よく使うフィールドが前半に並んでいる。 受信のたびに読む state / ポート番号 / シーケンス番号が先頭付近にあります。
  3. パディングが明示してある。 コンパイラ任せにせず、意図を残しています。

ただし正直に書くと、64 バイトに揃えたことによる性能向上は測定できません でした。それでも維持しているのは、「キャッシュラインをまたいでいるせいでは」 という疑いを今後毎回検討し直さずに済ませるためです。

19.2 netaddr_t — IPv4 と IPv6 を同じ型で持つ

typedef struct {
    uint8_t family;   /* NETADDR_V4 か NETADDR_V6 */
    uint8_t a[16];    /* IPv4 なら a[0..3] だけ使う */
} netaddr_t;

この型のまま持ち回り、ヘッダを組み立てる直前にだけ種別を見て分岐します。 接続の照合(4 つ組の比較)も、この型のまま行います。

IPv6 対応でこの型を導入したとき、1 コマンドあたり約 180 ナノ秒の固定 コストが乗りました。小さい読み出し(1 コマンド 3.3 マイクロ秒)では 5.5% の低下として観測されます。試して効果が無かった対策も 記録されています(第 24 章)。

19.3 nvmet_ctx_t — ターゲットの全状態

ターゲット 1 台ぶんの状態が全部入った、巨大な構造体です。

typedef struct {
    nvmet_tcp_conn_t admin;      /* admin キューの接続 */
    nvmet_tcp_conn_t io;         /* IO キューの接続 */
    uint32_t  cc;                /* コントローラ設定レジスタ */
    ...
    uint32_t  kato_ms;           /* Keep Alive の上限 */
    uint64_t  last_cmd_tick;     /* 最後にコマンドが来た時刻 */
    int       aer_pending;       /* 保留中の通知要求 */
    ...
    nvmet_ns_t ns[2];            /* 名前空間 2 つ */
    uint8_t   ram_disk[256MB];   /* 名前空間 1 の実体 */
    uint8_t   ram_disk2[32MB];   /* 名前空間 2 の実体 */
    uint8_t   id_ctrl[4096];     /* Identify の応答(組み立て済み)*/
    ...
    uint64_t  stat_read_bytes;   /* SMART 用の統計 */
    uint64_t  stat_write_cmds;
} nvmet_ctx_t;

設計上の判断が 2 つあります。

(1) 応答を先に組み立てておく

id_ctrl(自分の仕様書)のような内容が変わらない応答は、 起動時に 1 回組み立てて置いておきます。コマンドが来たらそれを送るだけです。

(2) 大きな配列は後ろに置く

ram_disk のような巨大な配列を前に置くと、後ろのフィールドが 遠くなってキャッシュに乗りません。よく使うものを前に集めています。

19.4 nvmet_ns_t — 名前空間

typedef struct {
    int      active;      /* 0 なら「番号はあるが使われていない」 */
    uint64_t lba_count;   /* 何ブロックあるか */
    uint8_t *disk;        /* 実体へのポインタ */
    uint8_t  id_ns[4096]; /* この名前空間の仕様書(組み立て済み) */
} nvmet_ns_t;

active が 3 つ目の状態を表しているのがポイントです。NVMe では 「範囲外の番号」と「範囲内だが使われていない番号」で応答が違います。 前者はエラー、後者はゼロ埋めの正常応答です。

19.5 受信用のリング

第 20 章 で説明する「push 型受信」のために、 受信処理と処理担当の間にリングバッファがあります。

typedef struct {
    uint8_t   kind;        /* コマンドか、データか */
    uint8_t   hdr[8];      /* PDU の共通ヘッダ */
    uint8_t   sqe[64];     /* NVMe コマンド */
    uint16_t  cid;
    uint32_t  dlen;
    uint8_t  *data_dst;    /* データが実際に置かれた場所 */
    ...
} nvmet_ready_t;

64 段あります。受信を担当する処理は「積む」だけ、送信は一切しない という分担です。

設計判断の例: この構造体に「Dataset Management の範囲リスト」を 入れる案がありましたが、やめました。4 キロバイトの配列を各段に持たせると 段の間隔が 4KB 開き、通常の読み書き(ホットパス)のアドレス変換に 負担がかかるからです。代わりに nvmet_ctx_t 側に同じ段数の配列を置き、 リングからはポインタで指しています。

第 20 章 1 つの I/O を最後まで追う

この章が第 V 部の主役です。Linux ホストが 8 キロバイト書き込むとき、 このプログラムの中で何が起きるかを最初から最後まで追います。

20.1 全体の流れ

 ① NIC がフレームを受信 → DMA でメモリへ
 ② mlx5_net.c が完了通知を見つける
 ③ netif.c が Ethernet ヘッダを見て IP へ渡す
 ④ ip.c が IP ヘッダを見て TCP へ渡す
 ⑤ tcp.c が順番を確認し、上位へ渡す
 ⑥ nvmet.c の受信担当が PDU を解析する
 ⑦ 「これは書き込みだ」と分かる
 ⑧ データを名前空間の実体へ書く
 ⑨ 完了(CQE)を組み立てて返す
 ⑩ TCP → IP → Ethernet と包んで NIC へ

20.2 push 型受信 — 呼びに行くのではなく呼ばれる

⑤から⑥への渡し方に工夫があります。

普通のやり方(pull 型)

/* 処理担当が「データある?」と聞きに行く */
n = tcp_recv(conn, buf, sizeof(buf), 0);
if (n > 0) { PDU を解析する }

この場合、TCP の受信バッファに一度溜めてから buf へコピーします。 コピーが 1 回発生します。

このプロジェクトのやり方(push 型)

/* 事前に「届いたらこれを呼んで」と登録しておく */
tcp_set_recv_upcall(conn, nvmet_io_rx_upcall, job_ctx);

こうすると、TCP がデータを受け取った瞬間にその場でこの関数 (upcall と呼びます)が呼ばれます。TCP の受信バッファを 経由しません。

20.3 ゼロコピー — 最初から目的地へ書く

push 型の本当の狙いは、コピーを 1 回減らすことではありません。 受け取りながら、最終的な置き場所へ直接書くことです。

nvmet_io_rx_upcall() は、届いたバイト列を状態機械で少しずつ解析します。

  PRX_HDR   : 共通ヘッダ 8 バイトを集める
      ↓ 集まったら「これは書き込みコマンドだ」と判明
  PRX_PSH   : NVMe コマンド 64 バイトを集める
      ↓ ここで「どの名前空間の、どのブロックへ書くか」が分かる
      ↓ ★ データの置き場所を「名前空間の実体の、その位置」に設定する
  PRX_DATA  : 以降届くバイトを、その場所へ直接書く

★の行が肝心です。この時点で最終目的地が決まるので、 データは中間バッファを一切経由しません。

  普通:   NIC → 受信バッファ → TCP のバッファ → 作業用 buf → 名前空間
                                                  (コピー 2〜3 回)

  これ:   NIC → 受信バッファ → 名前空間
                                (コピー 1 回)

読み出し側も同様で、名前空間の実体を送信元として直接指定します (nvmet_tcp_send_c2h_async())。

20.4 データの検査値もその場で計算する

第 14 章 のダイジェスト(CRC32C)を使う場合、素朴に実装すると 「全部受け取ってから、書き込んだ先を読み直して計算する」となります。 メモリを 2 回読むことになり、遅くなります。

このプロジェクトは、受信ストリームから逐次 CRC を積みます。 コピーしながら同時に計算するので、2 回目の読み出しが要りません。

送信側も同様で、送信元バッファから直接計算し、4 バイトを 追加でキューに積むだけです。

以前はダイジェストを有効にすると、この 2 つの高速パスが両方とも 無効になる作りでした。「ダイジェストなら使わない」という単純な条件分岐が 入っていたのです。直した結果、ヘッダのダイジェスト単体のコストは 誤差の範囲まで消えました(以前は書き込みが 31%、読み出しが 55% 遅く なっていましたが、その全部が高速パスを使わなかったことによるものでした)。

20.5 送信担当と受信担当を分ける

push 型の upcall は、TCP の受信処理の途中で呼ばれます。 ここで送信をすると、受信処理の中から送信処理が始まり、 その中でまた受信が…という再入が起きかねません。

そこで、upcall は「解析して、リングに積む」だけにしています。 実際の応答は、ジョブのステップ関数(冷たい経路)が リングから取り出して行います。

   TCP の受信処理
        │
        ├→ upcall : 解析してリングに積む(送信は一切しない)
        │
   ジョブのステップ
        │
        └→ リングから取り出して処理し、応答を送る

これが 第 19 章 の nvmet_ready_t の役割です。

20.6 書き込みの 2 つの経路

第 14 章 で説明したとおり、書き込みのデータの運び方には 2 通りあります。両方とも上記のゼロコピーが効きます。

 (a) in-capsule(コマンドと一緒に届く)
     upcall がコマンドを解析 → 置き場所を決める → その場に書く
     → リングに「完了」を積む → ジョブが CQE を返す

 (b) R2T(あとから届く)
     upcall がコマンドを解析 → 「これは R2T が要る」
     → リングに積む → ジョブが R2T を送る
     → データの PDU が届く → upcall が「どのコマンドのぶんか」を照合
     → 置き場所を決めて、その場に書く
     → リングに積む → ジョブが CQE を返す

(b) では「今どのコマンドのデータを受け取っている最中か」を 覚えておく必要があります。これが nvmet_pending_write_t です。

20.7 読み出しの流れ

 ① upcall がコマンドを解析(「読み出し」と判明、データ長は 0)
 ② リングに積む
 ③ ジョブが取り出す
 ④ 範囲を検査(名前空間の外なら「範囲外」のエラー)
 ⑤ 名前空間の実体を送信元として C2HData を送る(コピーなし)
 ⑥ 完了を送る

読み出しのほうが単純です。受信でゼロコピーが効くのは書き込み、 送信でゼロコピーが効くのは読み出し、という対称な関係になっています。

第 21 章 マルチコアの使い方

21.1 コアの割り当て

このプロジェクトは、インターフェースごとに担当コアを決めます。

  コア 0 : シェル(対話、コマンドの実行)、イニシエータ側のジョブ
  コア 1 : mlx5-pf1(ターゲット側)のジョブ
  コア 2, 3 : 予約(今は使っていない)

ジョブには「どのコアで動かすか」を指定でき、スケジューラは 自分の担当のジョブだけを実行します。

21.2 コアをまたぐときの約束

別のコアが動かしているジョブのデータを、横から触ってはいけません。

具体例を 2 つ挙げます。

(1) シェルから名前空間を追加するとき

シェル(コア 0)で nvmens add 2 と打つと、名前空間が増えます。 このとき第 12 章 の AER でホストへ通知する必要がありますが、 その送信はコア 0 からしてはいけません。ターゲットの admin キューは コア 1 のジョブが受信ポーリングしているからです。

そこで、シェルは旗を立てるだけにしています。

ctx->aer_notify_ns = 1;        /* コア 0: 旗を立てる */
        ...
/* コア 1 のジョブのステップ関数の先頭で */
if (ctx->aer_notify_ns && ctx->aer_pending) {
    通知を送る;
    ctx->aer_notify_ns = 0;
}

(2) Keep Alive の時間切れで接続を畳むとき

admin キューのジョブ(コア 1)が時間切れを検出しますが、 IO キューのコネクションは IO キューのジョブに畳ませます。 横から閉じると、受信 upcall の登録解除などの後始末が抜けるからです。 ここでも旗を使います。

21.3 旗を使うときの注意

旗は volatile int で持ちます。ただし volatile だけでは 「別コアから必ず見える」保証にはなりません(コンパイラの最適化は 防げますが、CPU のキャッシュ整合の話は別)。x86 はキャッシュの整合を ハードウェアが保証するアーキテクチャなので、この用途では実用上問題に なりません。

もっと重要なのは旗を消すタイミングです。

実際に踏んだ不具合: 旗を立てた側が直後に消してしまい、 受け取るはずのジョブが一度も見ないまま終わったことがあります。 旗を消すのは、受け取った側の役目にすべきです。

21.4 使っていないコアの準備

smp_boot_core2() / smp_boot_core3() という関数があります。 現在どこからも呼ばれていません。

これは「複数の接続の受信を複数コアへ振り分ける」将来の拡張のために 意図的に残してあるものです。一度、未使用の関数を一括削除する作業で 消してしまい、復活させた経緯があります。 リンク時に使われない関数は 除去されるので、残しておくコストはゼロです。

22.1 測っているもの

22.2 数字を読むときの注意

(1) 単位は MiB/s(1024 進)です

MB/s(1000 進)ではありません。約 4.9% 違います。

(2) 測定条件が違う数字を比べてはいけません

README.md の性能表には、100 ギガビットのカードで 2 ポートを直結して いた時期の数値が載っています。現在の構成は 25 ギガビットのカードで、 しかも 2 本のケーブルが別の機械(Raspberry Pi 5)を経由しています。 Pi5 側の接続が細いため、約 800 MiB/s で頭打ちになります。

この 2 つの数字を並べて「遅くなった」と判断してはいけません。 条件がまったく違います。

(3) 1 回目は低く出ます

起動直後の 1 回目は、キャッシュが温まっていないぶん低く出ます。 同じセッションで連続して測り、定常値を比べます。

(4) ばらつきが大きい項目があります

特に書き込みの 8 キロバイトは、同じバイナリ・同じセッションでも 942 / 0.01 / 595 MiB/s といった桁違いのばらつきが出ることがあります (0.01 の回は自己修復する既知の現象)。性能の退行判定にこの項目は 使えません。 64K / 256K と読み出しの 8K で判断します。

22.3 比較対象

第 23 章 速い理由

第 2 章 で「カーネルを通さないから速い」と書きましたが、 それだけではありません。積み重なった工夫を挙げます。

23.1 ゼロコピー

第 20 章 で詳しく説明しました。受信は最終目的地へ直接、 送信は最終的な置き場所から直接。

効果を実感するには、逆の実装を考えてみてください。8 キロバイトの書き込みで コピーが 3 回あれば、24 キロバイトぶんのメモリ帯域を使います。 1 秒に 3 万回なら 720 メガバイト/秒 — 転送量とほぼ同じだけの帯域を コピーだけで消費します。

23.2 ポーリング

第 3 章 のとおり、割り込みを使わず回り続けます。 反応が速く、割り込み処理のコストもありません。代償は CPU の占有です。

23.3 NIC へのオフロード

(1) チェックサム

第 6 章 のとおり、IP と TCP のチェックサム計算を NIC にやらせます。 CPU が全バイトを舐める必要がなくなります。

(2) LSO(Large Send Offload)

これが大きい工夫です。64 キロバイトのデータを「1 個の指示」として NIC に渡すと、NIC が MTU に合わせて分割し、それぞれに TCP ヘッダを 付けて送ってくれます。

  ソフトウェア:  [ 64KB のデータ ] + 「MSS は 9216 で切って」
                          ↓
  NIC:  [hdr|9216B][hdr|9216B][hdr|9216B]... と 8 個に分けて送出

シーケンス番号とチェックサムも NIC が正しく振り直します。 ソフトウェアの仕事が 1/8 になります。

23.4 CRC32C の実装

第 14 章 のダイジェストで使う CRC32C は、 x86 の専用命令(SSE 4.2 の crc32)があります。しかしこの命令には 「結果が次の入力になる」という依存があり、 単純に使うと 1 サイクルあたり 2.67 バイトが上限です。

そこでデータを 3 つに分けて、3 本の計算を交互に回します。 依存が切れるので、命令の遅延を隠せます。最後に 3 本の結果を合成します。

合成には PCLMULQDQ(キャリーなし乗算)命令を使います。

測り方を間違えた記録: 当初、64 キロバイトを 1 回計算する形で測って 「合成に専用命令は不要」と結論しました。しかし実際の呼ばれ方 (TCP のセグメントごとに細かく呼ぶ)で測り直すと逆でした。 汎用的な方法だと 1 回あたり約 30 マイクロ秒かかり、細かく呼ぶと 本体の速さを食い潰していたのです。

実装が実際にどう呼ばれるかと同じ形で測る必要があります。

正しさは起動時の自己テストで確認しています。既知の答えとの照合に加えて、 開始位置を 0〜7 バイトずらした 4096 バイトすべてについて、 1 バイトずつ計算した基準値と一致することを確かめます。

この全パターン検証が無かった頃の穴: 1 パターンしか検証しておらず、 自作イニシエータと自作ターゲットだけで試すと、両側が同じ間違い方を するので絶対に検出できない状態でした。

23.5 無駄なパケットを出さない

第 10 章 10.6 の (3) で説明した「情報の変わらない ACK を送らない」。 これだけで書き込み性能が 20% 上がりました。

23.6 同時 RDMA_READ の本数

第 15 章 15.3 のとおり、この設定を直したことで RDMA の書き込み性能が 2.3 倍になりました。

23.7 データ構造の配置

第 19 章 のとおり、よく使うフィールドを前に集める、 接続の照合でポート番号を先に比べる(アドレスより短くて弾きやすい)、 といった細かい調整をしています。

IPv6 対応で乗った 180 ナノ秒の固定コストのうち、これらの調整で 約半分を取り戻しています。

第 24 章 測って初めて分かったこと

この章は、推測が外れた記録です。設計の参考になります。

24.1 代表的でない条件で測ると逆の結論が出る

第 23 章 23.4 の CRC の話です。 「実装が実際にどう呼ばれるかと同じ形で測る」。

24.2 コストの所在は「無効化して測る」と一発で分かる

ダイジェストのコストが「プロトコル処理」なのか「CRC の計算」なのかを 知りたいとき、CRC の関数を「何もしない関数」に差し替えて測りました。

送信側も受信側も同じ関数を使うので、ダイジェストの値は自己矛盾なく一致 します。結果、プロトコル処理が約 3%、CRC 計算が 86% と切り分けられました。

憶測で最適化先を決めない。

24.3 効果が無かった対策の記録

IPv6 対応で乗った固定コストを取り戻そうとして、 試したが効果が無かったものです。同じことを繰り返さないための記録です。

試したこと結果
IP ヘッダを右詰めして TCP ヘッダの位置を種別に依存させない逆に 6〜9% 遅くなった。IPv4 のフレーム開始が 64 バイト境界から外れたため。撤回
接続の構造体を 64 バイト境界に揃える差が出なかった(それでも維持している。理由は 第 19 章)
受信時のアドレス生成を遅延させる差が出なかった(正しさのため残置)

効果があったもの: よく使うフィールドを前へ移動、接続の照合で ポートを先に比較、未使用領域のゼロ埋めを廃止、分岐ヘルパの インライン化。合計で相当量を回復しました。

24.4 ハードウェアが黙って直していたものは、止めた瞬間に出る

第 6 章 と 第 11 章 で触れた話です。

IPv6 の断片化を実装したとき、NIC のチェックサムオフロードが 拡張ヘッダを理解できずに間違った位置へ書き込むことが分かり、 その場合だけオフロードを外しました。

するとソフトウェア側の別のバグが露出しました。 疑似ヘッダの送信元 アドレスを間違えていたのですが、それまではNIC が正しい値で上書き していたので誰も気付かなかったのです。

そして同じ間違いが IPv4 側に残っていました。 IPv6 のときに手当てを したのに、IPv4 の断片には掛けたままだったのです。こちらは 受信側の組み立てを実装するまで、誰にも見えませんでした -- 自分で割ったものを自分で捨てていたので、壊れていても誰も読まなかった からです。組み立てを実装した初日に、テストが 「UDP のチェックサムが合わない」で落ちて発覚しました。

教訓: 受信側で確かめられない送信機能は、片側だけ実装している間は 必ず腐ります。

24.5 「動くはず」で機能を切ると、動くものを落とす

第 11 章 11.4 の話です。「NIC の機能は古い規格前提だろう」と 推測して IPv6 でオフロードを切ったところ、実際には動きました。 切っていた間、書き込みが 38%、読み出しが 47% 遅くなっていました。

切る前に一度有効にして測る。

24.6 誰も見ていない数字がある

第 10 章 10.6 の (3)、419 万個の無駄な ACK。 機能としては正常に動いていたので、カウンタを仕込むまで誰も 気付きませんでした。

このプロジェクトに ts_log(時刻付きのリングバッファ)や各種の カウンタが組み込まれているのは、こういう「見えていないもの」を 見えるようにするためです。

第 27 章 自己検査コマンド

27.1 なぜ自己検査が要るのか

第 2 章 2.3 で触れたとおり、このプロジェクトでは tcpdump も netstat も使えません。カーネルの外で通信しているからです。

そこで、自分で自分を検査するコマンドを組み込んでいます。 *test という名前のコマンドがそれです。

27.2 陰性対照と陽性対照

検査を設計するときの一番大事な考え方です。

「起きないはずのことが起きなかった」だけでは、検証になりません。 検査処理が一切動いていなくても、それは成立するからです。

たとえば第 7 章 の重複アドレス検出。「自分のアドレスは空いている」 という結果は、検出処理が何も動いていなくても得られます(応答が来ない ことで判定するため)。

そこで 陽性対照 を組にします。 「対向ポートのアドレスは使用中と判定される」ことを同時に確かめれば、 検出処理が本当に動いていることが分かります。

逆に 陰性対照 も要ります。たとえば 第 11 章 の MLD では、mld off で送信を止めると 通信が 100% 止まることを確かめます。これがあって初めて 「MLD が効いている」と言えます。

陰性対照そのものが間違っていた例: IPv6 のアドレス自動設定の検査で、 「不正なプレフィックス長」の陰性対照を作るとき、正しいデータの 長さだけを変えて使い回しました。ところがそのデータ自体が 別の規則に違反していたため、意図した理由とは違う理由で失敗して いました。陰性対照は「試したい性質以外は正しい」形にする必要があります。

27.3 主な検査コマンドの中身

rsttest — 閉じたポートへ接続し、経過時間で判定します。 「失敗した」だけを見ると、第 10 章 の RST が無くても 再送の時間切れで最終的には失敗するので、退行を検出できません。 200 ミリ秒以内に失敗することを条件にしています。

arptest — 有効期間を一時的に 600 ミリ秒に縮めて、 期限切れ → 確認 → 延命 / 破棄の流れを追います。終わったら元に戻します。

routetest — 別のサブネットの宛先を作るために、 同じ物理ポートを共有する「別名インターフェース」を一時登録します。 決定的な証拠は「どの IP を問い合わせたか」(最終宛先ではなくゲートウェイ) です。アドレスの計算だけを確かめても、宛先とゲートウェイが同じでは 検証になりません。

fragtest — 分割された断片そのものを見るために、 上位へ渡す途中に観測用のフックを挟んで中身を確かめます (組み上がった結果からは「何個に割れたか」が見えないためです)。 2 個に割れるだけでは通らない経路(中間の断片)を必ず通すようにしています。 最後に受信側が組み立てて上位へ渡すところまで通します。

組み立ての確認は、本物の分割器に割らせるのが本筋です。 自分で割って 自分で組み立てると、両方が同じ勘違いをしていても一致してしまいます (第 29 章 29.2)。fragrecv でポートを待ち受け、Linux 側から 2 万バイトの UDP を送って割らせました。IPv4(3 つに分かれる)と IPv6 (拡張ヘッダで分かれる)の両方で、長さも中身の総和も一致しました。

陰性対照は ext6test の「最初の断片だけを渡したら上位へ渡さない」です。 これが無いと、組み立てずに素通ししているだけの実装でも通ります。

backlogtest — 「受け皿を用意する前に SYN が届く」状況をわざと作り、 確立までの時間で判定します(第 10 章 10.8)。 陰性対照として待ち行列を 0 にした場合(取りこぼして 1.5 秒かかる)、 陽性対照として SYN|ACK を 1 個落とした場合(送り直しで 0.5 秒で回復)を 同じ検査の中で通します。64KB のデータは accept より前に送ります —— 待ち行列に居る間に届いたデータが引き渡しで失われないことを見るためです。

tcptstest — わざとロスを注入した状態で、往復時間の推定が何回 更新されたかをタイムスタンプの有無で比べます(第 10 章 10.9)。 ロスを注入しないと効果は 1 つも見えません —— ロスが無ければ タイムスタンプが無くても往復時間は測れるからです。

sacktest — ロス率を 200 個に 1 個 → 12 個に 1 個と振って、 SACK ありとなしで同じ量を送りきる時間を比べます(第 10 章 10.10)。 1 つのロス率だけで比べても意味がありません —— 効き方はロス率によって 変わるからです。判定に再送の個数ではなく時間を使うのは、 注入されるロスの数が走行ごとに違う(送ったセグメント数に比例する)ためです。

txdrop / synackdrop — 検査ではなく道具です。直結のリンクでは パケットのロスがまず起きないので、わざと捨てないと再送の実装を検証 できません。だから一時的なデバッグ機能ではなく、恒久的に残してあります。 前者はデータを持つセグメントだけを、後者は SYN|ACK だけを捨てます (握手そのものを落とすには後者が要ります)。

27.4 状態を変える検査は必ず元に戻す

arptest(有効期間)、routetest(経路)、pmtutest(経路 MTU)、 nudtest(有効期間)、backlogtest(待ち行列の深さと SYN|ACK の破棄)、 tcptstest(タイムスタンプの有効/無効とロス注入)、 sacktest(SACK の有効/無効とロス注入)、 termtest(チェック値の破壊)は、 いずれも設定を書き換えてから元に戻します。途中で失敗しても復元します。

ただし完全ではありません。経路 MTU の消去は、 すでに確立している接続のセグメントサイズを元に戻しません。 接続を張り直す必要があります。

28.5 認証について

NVMe-oF の実運用では、接続時の認証が必要です。方式は 2 つあります。

  • DH-HMAC-CHAP: 合言葉による認証。HMAC-SHA256 と Diffie-Hellman 鍵交換が要ります。
  • TLS 1.3: TCP の上に暗号化の層を追加。鍵交換・証明書・AES-GCM の一式が要ります。

このプロジェクトには crc32c.c 以外に暗号の実装が 1 つもありません。 ハッシュ関数と大きな数の演算をゼロから持ち込むことになります。

判断としては、やるなら DH-HMAC-CHAP のみ、TLS は対象外が妥当です。 それでも他の項目とは規模が 1 桁違います。

第 29 章 検証の考え方

このプロジェクトが積み上げてきた検証の手法をまとめます。 似た環境で開発する人の役に立つはずです。

29.1 根本の問題 — 自作どうしでは検出できない

自作のイニシエータと自作のターゲットだけで試すと、 両側が同じ間違い方をするので、絶対に検出できない不具合があります。

実例:

  • CRC の計算: 両側が同じ間違いをすれば値は一致します
  • メッセージ中のアドレスの位置が 4 バイトずれていた(第 11 章): 送る側も読む側も同じだけずれているので、全部通ります
  • 切断の手順(第 16 章): 自作のイニシエータがその手順を 踏まないので、ターゲットの不備が表に出ません

この問題への答えが、以下の 7 つの手法です。

29.2 手法 1: 相手側の構造体でパースさせる

このリポジトリのコードを一切使わず、Linux のヘッダファイルだけで バイト列を読み直すプログラムを書きます。

tools/disc_log_check.c   … Linux の <linux/nvme.h> だけを使う
tools/ip_frag_check.c    … <netinet/ip.h> だけを使う
tools/icmp_mtu_check.c   … <netinet/ip_icmp.h> / <netinet/icmp6.h> だけ
tools/ra_check.c         … <netinet/icmp6.h> の RA 構造体だけ
tools/mld_check.c        … libc の MLD 構造体だけ
tools/ip6_ext_check.c    … <netinet/ip6.h> の拡張ヘッダ構造体だけ

シェルコマンドに dump を付けると 16 進で出力されるので、 それをこれらのプログラムに食わせます。

役目は「フィールドの配置の検算」に絞ります。 値が仕様を満たすかの 判定は受信側の責任です(検査のために意図的に不正な値を入れることが あるため)。

注意: この道具を書くときにも間違えます。glibc の一部のマクロは ネットワークバイト順のまま掛ける定数で、変換後の値に掛けると 壊れます。実際にこれで正しい実装を「間違い」と判定したことがあります。

29.3 手法 2: 本物のホストに読ませる

Raspberry Pi 5 に Linux と nvme-cli が入っているので、 25 ギガビットのケーブル越しに接続して、本物の実装に解釈させられます。

これは手法 1 より強い検証です。Linux のカーネルと nvme-cli が、 実際にこのバイト列を読んで、フィールド名つきで展開して表示します。 配置を間違えれば「別のフィールドに値が出る」形で必ず見えます。

NVMe の機能(第 IV 部)の検証は、ほぼこの方法で行っています。 そのため、後半の実装では手法 1 の道具を新しく作っていません。

29.4 手法 3: 相手側の状態を相手側のツールで読む

このプロジェクトの動作が、相手側に状態を作ることを利用します。

例: Pi5 のネットワークブリッジを「マルチキャストを学習するモード」に すると、こちらが送った参加表明が Pi5 の bridge mdb show に載ります。

自作のプロセスを止める → エントリが消える
自作のプロセスを起動する → 3 秒で現れる

この因果関係が証拠になります。

29.5 手法 4: 陰性対照と陽性対照

第 27 章 27.2 で説明したとおりです。 「起きないはずのことが起きなかった」だけでは検証になりません。

さらに、機能を止める手段を恒久的に残すという手もあります。 mld off(参加表明を止める)や txdrop(パケットを捨てる)がそれで、 止めると通信が 100% 死ぬことが、機能が効いていることの証明になります。

29.6 手法 5: 届かないメッセージを自分で注入する

「ルータからのエラー通知」のように、この実験環境では誰も送ってこない メッセージがあります。これは対向のポートにルータ役をさせて注入します。

受信して処理する側が実装範囲なら、注入する側がテストコードでも成立します。 ただし注入する形式も自作になるので、手法 1 と組で使います。

29.7 手法 6: 相手側に「自作でない送り手」を書く

Pi5 に Python で AF_PACKET(生のフレームを扱う仕組み)のスクリプトを 置いて、本物の送り手を用意します。

tools/send_ra.py     … IPv6 のルータ役
tools/sniff_mld.py   … こちらの参加表明を観測する
tools/sniff_neigh.py … 近隣の問い合わせがユニキャストか観測する
tools/udp6_echo.py   … 断片化した UDP を組み立てさせる

受信側を書けば、自作の送信がワイヤに出ているかを相手側から確認できます。

Python で生フレームを扱うときの落とし穴が 3 つありました。 どれも「送信は動くので、受信を書くまで気付けない」ものです。 プロトコル番号を省くと 1 フレームも受信できない、変換関数を 掛ける場所を間違えると二重変換になる、ブリッジのポートでは 「全プロトコル」を指定しないと届かない。

29.8 手法 7: 途中の姿が見たいなら、通り道にフックを挟む

組み上がった結果からは分からないこと(IP の断片が何個に割れて、 中間の断片のオフセットがいくつか)は、通り道に観測用のフックを挟んで テスト側が仕様を見ながら組み直します。

もともとこれは、受信側の組み立てが未実装だった頃に 捨てる直前へ挟んだ苦肉の策でした。組み立てを実装したあとも フックは残してあります -- 往復が成功することと、途中の形が正しいことは 別の話だからです。

そして「片側だけ実装している間は必ず腐る」ことも分かりました。 受信側を実装した途端、送信側が壊れていたのが露見します (第 24 章 24.4)。

29.9 検証の設計で繰り返し間違えたこと

(1) 陰性対照そのものが規則違反だった

第 27 章 27.2 の例です。陰性対照は「試したい性質以外は正しい」 形にする必要があります。

(2) 値の解釈の間違いは、配置の検算では見つからない

第 16 章 16.5 の「0's based」の話です。バイトの位置は合っている のに意味が違う、という間違いは手法 1 では検出できません。 実データで境界を確かめる必要があります。

(3) 代表的でない条件で測る

第 24 章 24.1 の CRC の話です。

(4) 「1 回だけ見る」検査

「エラーが 0 件だった」は、そもそも検査が動いていなくても成立します。 接続直後・処理後・異常発生後の 3 点で比べるといった形にします。
